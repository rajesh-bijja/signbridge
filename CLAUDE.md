# SignBridge — Claude AI Documentation

Guidance for AI assistants working in this repository. These instructions describe **SignBridge** specifically.

## What this project is

**SignBridge** is a self-hosted tool for **presigning and invoking AWS and generic REST APIs**. It performs AWS SigV4 signing across four credential sources — IAM user keys, AWS SSO / IAM Identity Center roles, an EC2 instance's own attached role (read over SSH + IMDSv2), and EKS IRSA service-account roles — produces presigned URLs (including for non-S3 AWS APIs), and can invoke endpoints directly. It also supports non-AWS REST calls (Basic auth, Bearer token, and unsigned "generic" requests). **Sandbox mode** adds a third way in: write Python/JS/TS/Java in an in-app IDE and run it against the same profiles in a throwaway container. **S3 World** adds a fourth: a bucket browser that can *show you what is inside an object* — parquet as a table, xlsx sheets, gzipped logs as text, archive listings — with a recursive, forgiving search the console does not have.

- **Tagline**: *Presign URLs. Invoke APIs. Bridge IAM & SSO roles.*
- **Signing engine name**: **SignBridge** (the `lib/` code).
- **Positioning**: think "Postman for AWS SigV4" — native SSO/IAM Identity Center signing, self-hostable/air-gapped, with MCP/IDE integration and optional AI chat.

It is a lift-and-shift of an older Oracle-JET-based signing app. The Oracle JET UI has been removed; the app is now served entirely from a React frontend at `/signbridge/dashboard`.

## Backend architecture (`server.js`)

- Loads `config.properties` via `properties-reader`.
- Mounts everything under a **route base** (`/signbridge`, from `app.routePrefix`).
- `authConfig.applyDefaultUserToRequest(req)` runs on every route (except `/mcp`) to stamp the single local user onto the request body/options/profile/settings. It is skipped for `/mcp` because that endpoint carries raw JSON-RPC bodies that must not be mutated (the MCP handler injects the user into each downstream API payload itself).
- Serves the React SPA: static assets from `frontend/dist`, and explicit client routes (`/dashboard`, `/chat`, `/sandbox`, `/s3world`, `/s3world/object`, `/profiles`, `/history`, `/favorites`, `/templates`, `/settings`, `/about`) all return `index.html`. **`spaRoutes` are exact paths, not prefixes** — a nested page such as `/s3world/object` needs its own entry or a refresh in that tab 404s. `GET /session` returns the local-user session for the SPA.
- **MCP over HTTP**: `POST/GET/DELETE /mcp` are handled by `mcp/mcpHttp.mjs` (loaded lazily via dynamic `import()` since it is ESM). A fresh stateless `McpServer` + `StreamableHTTPServerTransport` is built per request; tools come from `mcp/tools.mjs`. This means one `node server.js` serves UI + REST API + MCP together.
- HTTPS only, TLS 1.2 (SSLv2/v3 and TLS 1.0/1.1 disabled). Certs come from `paths.getKeysDir()` (`<baseDir>/keys`); `certUtils.ensureCerts()` auto-generates a self-signed pair there on first run if missing.
- **The network surface is the authorization boundary, so `lib/netGuard.js` owns three decisions** (see **Network posture** below): `resolveBindHost` (default **loopback**), `isHostAllowed` (a `Host`-header allowlist, the DNS-rebinding defence) applied as middleware ahead of the routes, and `securityHeaders` on every response. There is no login, so binding elsewhere publishes the user's AWS credentials — `describeBindExposure` words the startup line for that, and it is a `WARN` only outside a container (see **Network posture** below).
- All runtime paths resolve through `lib/paths.js` — the base dir is **fixed** at `~/.signbridge` (`path.join(os.homedir(), '.signbridge')`), not configurable. Never build artifact paths from `os.homedir()` directly; use the `paths` module.
- On startup (and on every `populateProfilesDetails`), `loadProfilesDaemon.loadHomeProfiles()` imports `~/.aws` profiles into the active user's artifacts. Imported IAM/SSO profiles get `syncToAwsConfig=true` by default. On re-import, the daemon reads the already-stored profile: if it already has a `syncToAwsConfig` key (the user made an explicit choice) the flag is omitted from the update payload so it is not clobbered; if the key is absent (a legacy profile predating the flag) the default `true` is backfilled.
- **Bidirectional profile sync ("Sync to AWS Config")**: the mirror of the import above. For **AWS IAM User / AWS SSO User** profiles only, a `syncToAwsConfig` flag causes `addProfileDetails`/`updateProfileDetails` to write the profile back to `~/.aws/config` (and IAM access keys to `~/.aws/credentials`, mode `0600`) via `lib/awsConfigWriter.js`, so it is usable outside SignBridge (e.g. AWS CLI). The write is a key-level INI merge (existing profiles, comments, and unmanaged keys preserved); a fresh section also gets `output = json` (only when the user hasn't already set `output`). A sync failure never fails the save — the profile is already in artifacts — and is surfaced to the client as `awsSyncWarning`. The checkbox defaults **ON** for a fresh profile (frontend `clearForm`); when editing it reflects the stored value. **Unsync on update**: if `syncToAwsConfig` is turned off and an AWS profile is updated, `respondWithOptionalAwsSync` (with `isUpdate=true`) removes it from `~/.aws/config` (+ credentials) but KEEPS it in artifacts — the user wants the profile in SignBridge without the AWS-config mirror. **Delete consistency**: `deleteProfileDetails` also calls `awsConfigWriter.removeProfileFromAwsConfig` for synced AWS profiles, removing the section from both `~/.aws/config` and `~/.aws/credentials` — otherwise the next import (which runs on every `populateProfilesDetails`) would resurrect the deleted profile. The writer resolves `~/.aws` first, then the Docker bind-mount `/var/www/.aws`, mirroring `loadProfilesDaemon`. **Mount requirement**: Docker must bind-mount the whole `~/.aws` **directory** (not individual `config`/`credentials` files) read-write, so the writer can create/update those files even when they don't exist yet on the host and have them propagate back. Both `docker-compose.yml` and `launchSignBridge` mount `~/.aws:/var/www/.aws`.
- **If `frontend/dist/index.html` is missing, the server refuses to start.** Build first: `cd frontend && npm install && npm run build`.

### Auth modes (`authnMode` values → labels from `appConfig.getAuthModeLabels()`)

The registry is `lib/authnModes.js` — a table where each mode carries `{mode, flag, aws, temporary, awsConfigSyncable}`. It is the *only* place the list lives backend-side; `frontend/src/authnModes.js` is its mirror (ESM, plus the display labels), and `mcp/tools.mjs` keeps a literal copy of the AWS subset because ESM cannot `require()` the CommonJS registry (pinned by `test/mcpProfileTypeTools.test.js`). Declaration order is meaningful: it is the order pickers render in, and the order `credentialProvider.resolveAuthnMode` falls back through when the caller names no mechanism.

- `sso_user` → AWS SSO / IAM Identity Center
- `iam_user` → AWS IAM User
- `ec2_instance` → AWS EC2 Instance Role
- `irsa` → AWS IRSA (EKS Service Account)
- `rest_basic_auth` → Basic Auth
- `rest_bearer_token` → Bearer Token (static token or OAuth2 fetch)
- `generic` → Generic REST (no signing)

### Credential resolution (`lib/credentialProvider.js`)

**One module turns `(profile, authnMode)` into AWS credentials, and adding an AWS profile type is a row in `lib/authnModes.js` plus a case here.** Four call sites used to hand-roll the same `if (sso_user) … else if (iam_user) … else 400` chain — `requestSigner` (presign + invoke), `s3/s3World`, `sandbox/sandboxService`, `awsCliUtils` — and `curlUtils` was a fifth. Adding two profile types that way would have been ten new branches that must stay in agreement about refresh buffers, error text and SSO authorize links.

The returned shape is uniform: `{ credentials: {accessKeyId, secretAccessKey, sessionToken?, expiration?}, region, profile, profileName, authnMode, expiresAtMs, temporary }`. **Downstream signers branch on whether a session token is present (`credentialProvider.hasSessionToken`), never on the mode name** — SSO, EC2 instance roles and IRSA all yield the same STS triple, so the existing `sso*` signers carry them unchanged and only long-lived IAM keys lack a token. That is why EC2 and IRSA required no new signer. `expiration` travels *with* the credentials (not only in the envelope) because the presigners cap `X-Amz-Expires` via `expiryUtils.capExpiryToCredentialLife`. Errors keep whatever the provider attached — notably `verificationUriComplete` and `ssoSessionExpired`, which the UI turns into an **Authorize** button; don't rewrap and drop those.

### EC2 instance-role profiles (`lib/ec2Utils.js`)

Signs with the credentials of an EC2 instance's *own* attached role, read from that box rather than configured here — so a developer can reproduce exactly what their service sees, without ever copying a key.

- **How it gets them.** SSH to the instance (`ssh2`, not the system `ssh` binary — no shell quoting, no known-hosts prompt to script around), then run the IMDSv2 sequence: `PUT /latest/api/token` with `X-aws-ec2-metadata-token-ttl-seconds: 21600`, then `GET /latest/dynamic/instance-identity/document` (account, region, AZ, instance id/type), `GET /latest/meta-data/iam/security-credentials` (the role name), and `GET /latest/meta-data/iam/security-credentials/<role>` (the credential triple + `Expiration`). IMDSv2's token step is not optional: a v2-only instance (increasingly the default) refuses the unauthenticated v1 read.
- **Profile fields**: `ec2InstanceEnabled`, `ec2Host` (IP *or* hostname), `ec2SshUsername`, `ec2SshPort` (default 22), and **either** `ec2SshPrivateKey` (+ optional `ec2SshPrivateKeyPassphrase`) **or** `ec2SshPassword` — never both. The form enforces this *by construction* (a radio group writes only the selected source) rather than by validating after the fact, so switching from a key to a password cannot leave a stale key behind.
- **Test Connection is part of saving, not a nicety.** `testEc2Connection` does the whole round trip and reports the instance metadata and role name on success, or the specific reason on failure (host unreachable / SSH auth rejected / no role attached / IMDS blocked). Credentials come back through `maskCredentials` — `accessKeyId` as `ASIA****1234`, no secret, no token.
- Credentials cache on the profile as `ec2RoleCredentials` and refresh through the same buffer logic as SSO (`EC2_CREDENTIAL_REFRESH_BUFFER_MS`).

### IRSA profiles (`lib/irsaUtils.js`)

Signs as an EKS **service account's** IAM role, so you can debug a pod's permissions as the pod has them.

- **kubectl is not required, and neither is anything else installed locally.** The obvious implementation shells out to `aws eks update-kubeconfig`, `kubectl get sa`, `jq` and `kubectl create token`; that would mean shipping kubectl in the container, keeping a kubeconfig, and failing in ways no user can debug. Instead the EKS Kubernetes API is called directly: it accepts a bearer token of the form `k8s-aws-v1.<base64url(presigned STS GetCallerIdentity URL)>` with `X-Amz-Expires=60` and a **signed** `x-k8s-aws-id: <clusterName>` header — which is precisely what `aws eks get-token` emits. `eks:DescribeCluster` supplies the endpoint and CA. If `x-k8s-aws-id` ever fell out of the *signature* the URL would still look right and the API server would answer 401 with nothing to point at, so `test/irsaUtils.test.js` asserts it appears in `X-Amz-SignedHeaders`.
- **The flow, and it is explicit at every step** (a button per step in the UI, a tool per step over MCP): pick a **base profile** (an ordinary `sso_user`/`iam_user` profile, used *only* to reach EKS and read the role — EC2 is excluded because its credentials come from a box that may be unreachable, and IRSA because that would be circular) → `listIrsaClusters` (`eks:ListClusters`) → `listIrsaServiceAccounts` (`GET /api/v1/serviceaccounts`, keeping those annotated `eks.amazonaws.com/role-arn`) → `describeIrsaRole` → `testIrsaConnection`. Region defaults to `us-east-1` and is a free-text autosuggest, not a closed list.
- **The trust policy is read, not assumed.** `describeIrsaRole` does `iam:GetRole`, URL-decodes `AssumeRolePolicyDocument`, and extracts the audience and trusted subjects from `Condition.StringEquals`/`StringLike` (keys are matched by `:aud`/`:sub` *suffix*, since they are prefixed with the OIDC provider host). Given a namespace and service account it also returns a `subjectCheck` that **names the trusted subjects on mismatch** — the difference between "AccessDenied" and "this role trusts `system:serviceaccount:prod:my-app`, not `default:my-app`". A denied `iam:GetRole` is *not* fatal: it returns `trustPolicyReadable:false` with the default audience, because blocking profile creation on an optional read would be worse than proceeding.
- **A cluster 403 names which of two RBAC verbs is missing.** `describeK8sForbidden` (pure, exported, tested) takes the `intent` every `kubernetesCall` now passes — `'list-service-accounts'` or `'create-token'` — because listing service accounts needs `list` on `serviceaccounts` while minting a token needs `create` on the **`serviceaccounts/token` subresource**, and read-only cluster roles like `view` grant the first but not the second. Lumping them together sends the user to fix an access entry that is already correct (if listing worked, the identity *is* mapped), so the create-token message says so and quotes the Role rule to add. A 401 is the genuinely different case — the bearer token was not accepted at all, i.e. no mapping — and gets the access-entry advice instead.
- **Minting**: `POST /api/v1/namespaces/{ns}/serviceaccounts/{name}/token` (an `authentication.k8s.io/v1` TokenRequest with the resolved audience), then an **unsigned** `sts:AssumeRoleWithWebIdentity` — unsigned is correct, the web-identity token *is* the credential.
- **Profile fields**: `irsaEnabled`, `irsaBaseProfileName`, `irsaBaseAuthnMode`, `irsaRegion`, `irsaClusterName`, `irsaNamespace`, `irsaServiceAccount`, `irsaRoleArn`, `irsaAudience` (blank = whatever the trust policy requires; the form omits the key entirely rather than persisting `''`, which would read as an explicit choice). Credentials cache as `irsaRoleCredentials`.

### Temporary credentials & presigned-URL expiry

- **Credential refresh (`lib/ssoUtils.js`, `getSecurityToken`).** SSO signing uses temporary role credentials cached on the profile (`roleCredentials.{accessKeyId,secretAccessKey,sessionToken,expiration}`, `expiration` is epoch **ms**). They are reused only while they have more than `CREDENTIAL_REFRESH_BUFFER_MS` (default **5 min**, env-overridable via `SSO_CREDENTIAL_REFRESH_BUFFER_MS`) of life left; otherwise they are re-minted before signing. A tiny buffer previously let nearly-dead credentials be reused, producing "fresh" presigned URLs that failed immediately with `AuthFailure`.
- **Expired-session message.** If re-minting fails and there's no device-authorization link to surface, `getSecurityToken` returns a clear, actionable error (`ssoSessionExpired=true`, statusCode 401) telling the user to run `aws sso login --profile <name>` and retry — instead of a cryptic failure. A pending-authorization error (with `verificationUriComplete`) is passed through untouched so the UI/chat render the clickable link.
- **Presigned-URL lifetime.** `X-Amz-Expires` comes from `options.expiresInSeconds` (see `generateAuthResponse` above). **For every temporary-credential mechanism** (`sso_user`, `ec2_instance`, `irsa`) the presigners (`lib/ssoPresigned.js`, `lib/ssoS3Presigned.js` — they serve all three, since all three yield the same STS triple) additionally cap `X-Amz-Expires` to the credential's real remaining life (`roleCredentials.expiration - now`), because a SigV4 request is valid only until the *earlier* of `X-Amz-Expires` and the session token's own expiry. So long expiries only take effect for **IAM-user** profiles (long-lived keys). The UI exposes this as the **Presigned URL Expiry** dropdown (`PresignDashboard.jsx`); chat/MCP expose it as `expiresInSeconds`. In S3 World the object viewer's **Presigned link** menu offers 5 min / 1 h / 12 h plus **Custom…**, an inline value + minutes/hours form; it validates against `MIN_EXPIRY_SECONDS`/`MAX_EXPIRY_SECONDS` (60 s … 43200 s, mirroring `clampExpiry`) and *refuses* an out-of-range value rather than letting the server clamp it silently — a link that quietly lasts 12 h when you asked for 20 is worse than a refusal. The copy confirmation always reports the lifetime the server actually granted, so an SSO cap is visible.

### Bearer Token profiles (`lib/restAuth.js`)

A bearer profile is either a **static** token or an **OAuth2 fetch** (`bearerTokenSource=oauth2`): fields (`grant_type`, `client_id`, …) POSTed to a token endpoint. For OAuth2:
- **"Token to use" is discovered, not guessed.** The UI hides the "Token to use" selector until **Test Connection** (`testBearerTokenConnection`) runs. On success the backend reports `availableTokens` and a grant-aware `recommendedTokenField` — `access_token` for `client_credentials`, `id_token` (falling back to `access_token`) for `password`. If the required token is absent the test fails with an explanatory error instead of silently picking one. Editing any token-fetch field re-arms the test (the selector hides again until re-tested). The chosen field persists as `bearerTokenResponseField`.
- **Auto-renew on expiry** (`bearerAutoRenewOnExpiry`, a checkbox): when set, an expired cached token is silently re-fetched at invoke time; when unset, invoking with an expired/absent token returns a clear 401 telling the user to enable auto-renew or re-run Test Connection. This is enforced in `resolveBearerToken(profile, { errorOnExpiry }, cb)` → `fetchOAuth2Token`, so it applies to **both** dashboard invokes and chat/MCP invokes (all share the same endpoint). Tokens are cached in-memory only, keyed by profile name — never persisted.

### LLM provider configuration (`lib/llm/`)

**The whole LLM configuration is a runtime setting, Settings is its only source, and nothing needs a restart.** The old design read one model from `config.properties [llm]` and one key from the process environment, which meant trying a different model was an edit-and-restart and the key lived somewhere the app could not verify, mask, rotate or attribute to a provider — while leaking into process listings, shell history and whatever orchestrator template set it. Now the user picks a provider in **Settings → AI features**, supplies a key, the key is verified, and the models that key can actually reach are listed to choose from. `llm.provider`, `llm.model` and `llm.baseUrl` are **dead keys**, and `LLM_API_KEY`/`LLM_MODEL`/`LLM_BASE_URL` are **gone** — do not reintroduce reads of any of them.

**There is no `[llm]` section left at all, and `LLM_ENABLED` is gone with it.** The on/off switch and the behavioural knobs (`reasoningEffort`, `temperature`, `maxToolIterations`) were the last things read from a file, and the switch was the worst of them: `settings.enabled` was written by `llmService` and rendered by the panel but **never read by `resolveActive`**, while the value that actually decided was `llmClient.isLlmEnabled()` reading `LLM_ENABLED`/`llm.enabled` at module load. So the toggle in the UI was decorative, and turning AI features off meant editing a file and restarting the container. All five now live in the user's settings, are clamped centrally by `llmSettings` (`sanitizeReasoningEffort`/`sanitizeTemperature`/`sanitizeMaxToolIterations` — clamped, not rejected, because a save that fails with no named field is worse than one that lands in range), travel on the resolution, and are editable in Settings → AI features. A turn resolves them when it runs, so a change applies to the next message. `test/llmConfig.test.js` comment-strips `llmClient.js`, `agent.js` and `llmSettings.js` and asserts none of them mentions `LLM_ENABLED`, reads a `props.get('llm.…')` or so much as requires `properties-reader`; `test/secretHygiene.test.js` asserts `config.properties.example` never regrows an `[llm]` section. **Do not add a config key or an environment variable that gates or overrides any AI setting** — a setting split between a file and a form is a setting where the form lies, and the failure is silent in the direction that matters (it works on the machine that added it, and the only person who notices is the user who flips the toggle and sees nothing happen).

Fifteen things to preserve:

- **`resolveActive()` decides whether a turn runs at all, so the enable switch lives there and nowhere else.** It is the one place that already knows every *other* reason a turn cannot start, a second gate would inevitably disagree with it, and any gate outside the stored settings is a value the user cannot change from the page that claims to own it. Off returns `ok:false, reason:'disabled'` with a message naming the toggle, and `chatService` gives it the same `503` + `needsLlmSetup:true` treatment as every other reason — deliberately, because now that the switch is in Settings, "disabled" is something the user can fix there (it used to be excluded, when it meant an operator had set `llm.enabled=false` in a file and pointing at Settings would have been a dead end). Two defaults are load-bearing: a **missing** `enabled` key reads as **on**, so an install predating the field does not silently lose chat on upgrade, and `emptySettings()` also defaults it to `true`, so a fresh install reports the actionable `not_configured` rather than `disabled` — "turn this on" is the wrong instruction when the real next step is picking a provider.
- **`resolveActive(settings)` takes the stored settings and nothing else — there is no environment fallback, and it must not grow one back.** It used to accept an `env` argument and fall back to `LLM_API_KEY`/`LLM_MODEL`/`LLM_BASE_URL` for an unattended deploy that could not reach the Settings page. That is deleted: a provider key in an environment variable cannot be verified, masked, rotated or attributed to a provider by the app, it is invisible to the Settings UI that is supposed to be the single source of truth about which provider answers a turn, and it sits in a process listing, a shell history and whatever orchestrator template set it. A fallback also has to carry its own model default (the deleted `DEFAULT_ENV_MODEL`), because a resolution with `ok:true` and `model:''` earns a `400 you must provide a model parameter` from every provider — i.e. the fallback's own failure mode is a broken deploy that looks configured. The honest alternative is what happens now: with nothing configured, `resolveActive` returns `ok:false, reason:'not_configured'` with a message naming Settings → AI features, `chatService` turns that into a 503 with `needsLlmSetup:true`, and both the Chat page and the Settings panel say so before the user types. `test/llmConfig.test.js` sets the three variables for real and asserts they are ignored, then comment-strips `llmSettings.js` and `llmClient.js` and asserts the names appear in neither. Failure is always a named `reason` (`disabled`, `not_configured`, `missing_key`, `missing_aws_profile`, `missing_model`, `provider_not_inference`, `missing_base_url`, `unknown_provider`) plus a `message` the UI shows verbatim.
- **The user is told a key is required, in the place they notice it.** Two surfaces, one source: `ModelPicker` reports the resolved state upward through an `onStatus` prop (gated on its own `loading`, so a slow settings fetch does not flash a warning at someone who is fully set up), and `ChatPanel` renders that as a warning banner above the composer linking to Settings — proactively, before a turn is sent, rather than as a 503 after one. `LlmSettingsPanel` shows the same `active.message` verbatim. This is the half of the removal that matters to a user: taking the fallback away is only correct if nothing fails silently in its place.
- **`toPublic()` is the only shape that reaches a client, and it has no `apiKey` property at all** — not an empty one. It carries `keyMask` + `hasKey` instead, which is what the UI needs to render "sk-proj-…••••fDIA — verified 2 minutes ago" and to decide between "Add key" and "Replace key". Relatedly, `setProviderConfig`'s `apiKey` semantics are three-way and load-bearing: `undefined` leaves the stored key alone (the browser never had it to send back — this is what makes "edit the base URL without re-entering the key" work), `''` clears it, a string replaces it.
- **Every response carrying `settings` also carries `active`.** Both frontends fold the two out of whatever came back, so a write that returned `settings` alone left the Settings panel and the model chip reading "no provider configured" *immediately after a successful test*, with another round trip the only way to learn otherwise. `respondWithSettings` + `publicActive` in `llmService.js` guarantee the pair; the hand-built responses (test failed/succeeded, model list) each attach it explicitly.
- **`looksLikeKey` is advisory and must stay that way.** Providers change key prefixes without notice, so it is consulted *only* inside `testConnection`'s success handler to attach a `warning` — never to gate a call or derive a failure. `test/llmProviders.test.js` inspects the source to assert its call site is preceded by `ok: true`, because "we refuse to send your key because it doesn't look like a key" is an unfixable dead end for the user.
- **Model filtering is a deny-list, and capability metadata beats the name.** `GET /v1/models` returns embeddings, TTS, moderation and image models, and offering `text-embedding-3-small` as a chat model is simply broken — but an allow-list would hide a new model the day it ships, which is the failure a user actually notices. So `NON_CHAT_PATTERNS` drops known non-chat families, OpenRouter's `architecture.output_modalities` and Google's `supportedGenerationMethods` are trusted over the id when present, and **if the filter removes everything the unfiltered list is returned** — an empty picker is worse than an imperfect one. (`'realtime'`, not `'realtime-preview'`: that family went GA and leaked into the picker.)
- **SignBridge is not a broker for provider credentials, and `ACQUISITION` has exactly two values because of it.** Every provider is set up the same way: paste a key you have, or follow the provider link, create one there and come back. Two flows that did otherwise were removed — an OpenRouter OAuth/PKCE exchange, and an OpenAI "mint" where the user pasted an organisation admin key (`sk-admin-…`) so SignBridge could create a project service-account key from it. Both were a man in the middle between the user and their own provider account: extra code paths that could hold a credential, one of them a credential that *creates more credentials*, in exchange for saving a copy-paste — and they made the one screen a new user has to understand behave differently depending on which tile they clicked. `test/llmProviders.test.js` fails if a third `ACQUISITION` value appears or a row regrows an `oauth`/`mint` config; `test/mcpLlmTools.test.js` fails if the routes come back. Do not reintroduce a flow where SignBridge creates or exchanges a provider credential.
- **Bedrock's OpenAI-compatible surface does not serve Claude, and this was measured rather than assumed.** `bedrock-runtime.<region>.amazonaws.com/openai/v1` is real, accepts a Bedrock API key as a plain bearer token, and this row used to point at it — but `GET /openai/v1/models` answers `404 <UnknownOperationException/>` (a *routing* error, so it is absent for every credential kind, not a permission) and a Claude model id posted to `/openai/v1/chat/completions` answers `404 "The model doesn't exist or doesn't support this API."` That surface is for the `openai.gpt-oss-*` models. Claude is reached through the **native Converse API** — `POST /model/{modelId}/converse` and `/converse-stream` — so the row is `kind: 'bedrock'`, carries no `baseUrl` at all (the endpoint is derived from the region), and `lib/llm/bedrockConverse.js` answers its turns. Do not "restore" a base URL here: the configuration verifies and then 404s on every Claude model, which looks like a model-access problem in the AWS console rather than a wrong endpoint.
- **The Converse adapter is deliberately not a `chatBackend`.** Converse has first-class tool use, so once the request/response shapes are translated, `agent.js`'s tool loop, the streaming emitter, the thread store and the quick-reply protocol all work unchanged. A backend would have meant a second copy of the loop to keep in agreement with the first. What the adapter owns instead: OpenAI messages → Converse (system prompts lifted to a top-level field, tool results turned into content blocks on a *user* message, consecutive same-role turns merged — Converse requires strict alternation, and a turn that called three tools is otherwise three consecutive user messages and a 400 that names validation rather than shape), the `application/vnd.amazon.eventstream` framing (pure and incremental: a frame straddling two TCP reads is the normal case), and the `contentBlockIndex` → `tool_calls[].index` renumbering (Converse indexes *all* content blocks, so with leading text the first tool use is block 1; passing that through leaves a hole at OpenAI index 0 that the agent accumulates into a tool call with no name). The request path is built from the **raw** model id: SigV4 canonicalises by encoding what is on the wire, so pre-encoding the colon in `…-v1:0` gives a signature mismatch that reads as a credential fault and reproduces only on the models that have one — i.e. all the current ones.
- **Bedrock signs as `bedrock`, never as `bedrock-runtime`.** The signing name is a separate field from the endpoint prefix in every botocore model, and where they differ, signing the hostname's first label produces `401 Credential should be scoped to correct service: 'bedrock'` — which names a credential and means a service name, so every profile type fails identically and the credentials look like the problem. The derivation now lives once in `lib/awsSigningName.js` (a pure function over the hostname plus a small override table), and all four presigners/invokers route through it, so `bedrock-runtime` also works from the dashboard, MCP and Sandbox. `test/awsSigningName.test.js` asserts no signer grows its own copy back.
- **Bedrock can sign with a SignBridge profile, and that is the default.** SignBridge already mints AWS credentials four ways (IAM user, SSO role, EC2 instance role, EKS IRSA service account) and Converse accepts all of them — the STS triple is the same one the `sso*` signers already carry — so Claude in the user's own account needs no new credential to create, rotate or store. Hence `credentialSources: [aws_profile, api_key]` with `aws_profile` as the default, resolved per request through `credentialProvider.resolveByProfileName` so short-lived credentials refresh mid-conversation without a reconnect. The API-key path stays, because a Bedrock API key is the simpler answer for someone who has one. Note this is the one provider where SignBridge holds two unrelated kinds of AWS credential in the same screen: a signing profile signs the AWS API calls made *for* the user, while a Bedrock API key only buys inference — conflating them would mean presigning with an inference key or spending model quota with a signing profile. Which is why the credential source is an explicit choice rather than "whatever is configured".
- **Invoking and listing are independent Bedrock permissions, so a denied model list is a passing test.** The role this was built against (an EKS `api-service` service account) has `bedrock:InvokeModel` but neither `bedrock:ListInferenceProfiles` nor `bedrock:ListFoundationModels`. Reporting that as a failed connection would send the user to debug credentials that work perfectly. So `testBedrockConnection` proves the credentials *resolve*, tries the two listings, and on a **403** passes with a `warning` naming the missing permissions and offers `fallbackModels(region)` — a deliberately short list of current Claude inference profiles — while a **401/400** (`rejectedNotDenied`) still fails, because for an API key no invoke is attempted and the listing is the only signal there is. There is deliberately **no test invoke**: it would need a model id, and the role may well be authorised for the model the user intends and not for whichever one we picked.
- **Every id in that fallback list was verified by invoking it, and it is stored as a suffix plus a region-derived prefix.** Three plausible spellings are wrong in ways that read as a permissions problem: `us.anthropic.claude-opus-4-6-v1` works while `…-v1:0` is `400 The provided model identifier is invalid`, `claude-sonnet-4-6` carries no version suffix at all, and there is no 4.6 Haiku. A bare `anthropic.*` id is refused as on-demand-unsupported, and an `eu.`-prefixed id is invalid from a US region — which is why `FALLBACK_MODELS` holds `{suffix, label}` rows and `crossRegionPrefix(region)` supplies `us.` / `eu.` / `apac.` / `us-gov.` / `global.` (GovCloud is matched *before* `us-`, since its regions start with both). The list stays short on purpose: a stale long list is worse than a few current ids plus the ability to type one in. `test/bedrockConverse.test.js` pins the prefix derivation and asserts the three disproved spellings never come back.
- **An identity that cannot list models can type a model id, and it is remembered — in the model picker itself, not beside it.** With no `bedrock:List*` there is no picker to choose from, so the Model field is a Cloudscape **`Autosuggest`** whose `enteredTextLabel` offers an unlisted id as `Use "<id>"` at the top of the same dropdown. It was briefly a `Select` plus a separate "Or use a specific model id" field, which is wrong for the case that motivated it: where listing is denied, typing an id is the *normal* path, not an escape hatch, and making it a second control asks the user which of two model fields they want. One control also means one handler — `handleSelectModel` serves both, since `selectLlmModel` accepts any string and remembers an unlisted one. The remaining `TokenGroup` is for *forgetting* an id only, and renders only when there is one. `selectLlmModel` already accepted any string, so what was added is *memory* — `customModels` on the provider config (`llmSettings.sanitizeCustomModels` / `rememberCustomModel`, capped at `MAX_CUSTOM_MODELS`), kept **separate from `models`** because that array is replaced wholesale on every refresh, which is exactly when the user needs their own id most. The id is deliberately **not** shape-validated: an inference-profile id, a bare model name and a provisioned-throughput ARN look nothing alike, and a validator that only knew today's shapes would reject the model the user came here to add. `modelsUsedFallback` (persisted by the test and by `listLlmModels`) is what lets `LlmSettingsPanel` stop calling the short list "available" and put the type-an-id field in front of the user rather than behind a disclosure; adding an id happens as a side effect of choosing it, so `updateLlmSettings({customModels})` exists only to *forget* one, and a key rotation deliberately leaves the list intact.
- **`chatBackend` is the escape hatch for a provider that is not reachable over HTTP at all, and it stays a two-site dispatch.** Bedrock above needed only a different *client*; Cursor needs a different *loop* — it sells an *agent*, so there is no `/chat/completions` to POST to and no way to reach the models a Cursor key pays for except by running Cursor's own agent. A row may therefore name a `chatBackend` (`'cursor-agent'` → `lib/chat/cursorAgent.js`) and is then answered by that module instead of the OpenAI client. Exactly two places branch on it: `llmClient.resolveSession`, which returns a **client-less** session (`client:null` plus `chatBackend`), and the `CHAT_BACKENDS` table in `chatService.js`. Nothing else may special-case a provider id — `providers.getChatBackend(row)` is the only reader of the field, and `test/llmProviders.test.js` asserts no other row grows one. The row also carries a `backendNote` the Settings card renders verbatim, because "this provider needs a CLI on the server" is not discoverable from a key field. Note `resolveActive`'s `provider_not_inference` branch is now unreachable (no row sets `inference:false`); it is kept as the guard for a future row that genuinely cannot serve chat, and `test/llmConfig.test.js` no longer asserts it rather than keeping a provider unusable to satisfy a test.
- **The mode of `<keysDir>/llm-secret.key` is part of the feature.** Encrypting the settings file is worth exactly as much as the wrapping key beside it, so the key is written `0600`, `docker-entrypoint.sh` keeps `keys/` at `0700`, and `secretStore` re-asserts `0600` on every read. That last one is not paranoia: the entrypoint used to run `chmod -R 775` over the whole base dir on every container start, which walked over the TLS private key, the wrapping key and the sealed settings file and left all three world-readable with nothing failing anywhere. **Never add a recursive `chmod` under the base dir** — `chown -R` is what the app needs, and `test/llmSecretPermissions.test.js` fails if one comes back.

**Frontend**: two components, and the split is deliberate rather than duplication — Settings is Cloudscape and Chat is react-bootstrap, so one shared widget would look like a defect on one of the two screens.
- `components/llm/LlmSettingsPanel.jsx` (Cloudscape, rendered by `PresignSettings.jsx`) — the **Enable AI features** switch, the provider tiles, the credential-source choice, the key card, Test connection, the model list, and the **Agent behaviour** card. The switch is now the only thing that turns chat off, so its off-state copy says the effect is immediate and that keys and the model choice are kept (the failure it prevents is a user flipping it and going looking for the config file they think is really in charge). The Agent behaviour card holds reasoning effort (a closed `Select` — unlike model or region, these are exactly the four values `reasoning_effort` accepts, so an unrecognised one is a 400 rather than a new capability), temperature and max tool iterations, and it is the one place in the panel that keeps **drafts** (`effortDraft`/`temperatureDraft`/`iterationsDraft` mirrored from `settings` by an effect): two of the three are free text, and saving per keystroke would persist `"1"` on the way to `"12"`. Its save notice says the change applies to the next message with no restart, because "did that take?" is the whole question a user has about a knob that used to live in a file. A provider offering more than one credential source (only Bedrock) renders a `SegmentedControl` above the key card, because it decides whether the key card is relevant at all; choosing **Sign with an AWS profile** replaces it with a profile picker, a mechanism picker (shown only when the profile offers more than one — a single-mechanism profile answers that question itself), a free-text region field, and its own Save & test button. The source choice is sent with the test, so Test also *saves* it: a green tick describing a configuration the next chat turn would not use is worse than no tick. "Configured" is therefore `isConfigured()`, not `hasKey` — a profile-signed provider never has a key, and reading its badge as unconfigured forever is worse than no badge. The key card is laid out as **two numbered options** and the headings say so: *Option 1 — I already have an API key* (the field, plus Save & test / Test the stored key / Remove key) and *Option 2 — I don't have a key yet* (a link to that provider's console and the instruction to come back and paste it into option 1). That structure *is* the answer to "which of these do I do?" — it used to be a key field with a console link below it and two expandable panels offering flows that created the key for you, and which of the four a given tile showed varied by provider. Switching provider changes only which one answers; other providers keep their stored keys, and the success notice names the handover ("Chat now uses Anthropic (Claude) instead of OpenAI, whose key stays saved") because a silent one is how "I connected Claude and it still answers as GPT" happens. A provider with a `chatBackend` renders two extra things, and both are about the half of the setup a key cannot express: its `backendNote` as an info alert ("how this provider answers"), and its `backendStatus` — the persisted result of the backend's own `preflight()`, attached by `testLlmConnection` — as either a "Ready: found `agent` (…)" line or a warning naming exactly what is missing. `handleTest` also appends *"but chat cannot use it yet, see the card below"* to the green notice in that case, so a verified key never reads as a working provider when it isn't. `tileDescription()` says the same thing one line earlier, on the tile itself.
- `components/llm/ModelPicker.jsx` (Bootstrap, rendered by `ChatPanel.jsx`) — the Cursor-style provider + model chip above the composer, with a searchable model list. **Selecting a model here writes back through `selectLlmModel`**, so the choice is the same one Settings shows; the turn also passes it as a per-request override so it applies without waiting for that write to land. Its gate is `inference !== false && verifiedOk` and deliberately ignores `backendStatus`: that field is only as fresh as the last Test connection, so hiding a provider whose CLI the user has since installed is worse than a turn that fails with an actionable 503.
- `frontend/src/llmProviders.js` mirrors the registry's id order and adds display labels, exactly as `authnModes.js` mirrors `lib/authnModes.js`. `test/llmProviders.test.js` pins the two together.

**MCP**: three read-mostly tools (`list_llm_providers`, `list_llm_models`, `set_llm_model`) and deliberately no more. An MCP client *is* an LLM, and no tool should let it write a credential or spend the user's provider quota creating another — so `testLlmConnection`, `deleteLlmKey` and `updateLlmSettings` are off limits. That omission is invisible by nature, so `test/mcpLlmTools.test.js` asserts both that `mcp/tools.mjs` never references those routes and that `server.js` still mounts them (and that the removed key-brokering routes stay removed on both sides).

### AI chat flow (`lib/chat/`)

The chat copilot is a **multi-turn, tool-calling agent** (Athena-style, hand-rolled and right-sized), not a one-shot planner. It reuses the *same* tool set the MCP server exposes (58 tools; `mcp/tools.mjs` is the one definition, and `test/mcpToolParity.test.js` keeps it level with the dashboard's routes). Every provider but one runs the loop *here*, in this process, over an OpenAI-shaped POST; a provider whose registry row names a `chatBackend` is handed to that module instead (`CHAT_BACKENDS` in `chatService.js`), which owns its own loop — see **Cursor as a chat backend** below.

1. `chatService.handleChat` resolves the user, gets-or-creates a thread via `threadStore` (`req.body.threadId`; a new one is created and returned if absent), and builds a streaming emitter over `coreUtils.emitToUser(userName, 'event_chat_stream_<userName>', …)`.
2. `agent.runTurn` runs the loop: `model → (tool calls?) → run tools → observations → model`, ending when the assistant returns a message with no tool calls (or the iteration cap is hit — `session.maxToolIterations`, which the user sets in Settings; `agent.js` reads no config file and keeps only a `DEFAULT_MAX_ITERATIONS` for a session that arrives without one). It streams token/tool events through the emitter.
3. Tools come from `mcp/tools.mjs` via `buildOpenAiTools(ctx)` — `ctx.callApi` is a loopback axios POST to this server's own HTTPS API (self-signed, `rejectUnauthorized:false`), so a chat invocation behaves exactly like a dashboard invocation. The agent decides which tools to call and chains them (e.g. `list_history` → read result → `invoke_api`).
4. `llmClient.resolveSession(userName, override, cb)` resolves the provider, key and model **per request** through `llmSettings.resolveActive` (see `lib/llm/` above) and hands back `{ ok, client, model, providerId, providerLabel, source, buildParams }`, or `{ ok:false, statusCode:503, reason, message }` when nothing is configured — the frontend keys its "open Settings" prompt off that 503. For a `chatBackend` provider it returns the same envelope with `chatBackend` set and **`client:null`**, deliberately: a null client makes "code that assumed an endpoint" fail immediately and loudly rather than POSTing to a URL that does not exist. Three details: the OpenAI client is cached by **base URL + hashed key fingerprint**, not once per process, because two providers or a rotated key must not share an HTTP agent configured for the old one; `buildParams` lives on the session rather than the module because the reasoning-vs-`temperature` decision depends on the *resolved* model (a global `getModel()` silently applied the config model's rules to whichever model was actually in use); and `override` (`{providerId, model}`) is what lets the in-chat picker take effect on the same turn it is used. **This module reads no config file and no environment variable at all** — not even `properties-reader`. `buildParams` takes `reasoningEffort`/`temperature` off the resolution and the session carries `maxToolIterations` to the agent, so all three are whatever the user last saved in Settings; anything read here instead would be a value the Settings page cannot change without a restart.
5. The active dashboard profile arrives as `req.body.activeProfile`; it is passed to the agent as a per-turn system context note **as a hint only**. The agent does NOT assume a profile: unless the user names one, it calls `list_profiles` and asks the user to choose (and, when a profile supports more than one auth mechanism, asks which mechanism) before invoking/presigning.
6. **Quick replies**: to ask the user to choose, the agent ends its turn with a fenced ```` ```quickreplies ```` JSON block `{ prompt, options: [{ label, value }] }`. `ChatPanel.jsx` strips that block from the rendered Markdown and shows the options as clickable chips; a click sends `value` as the next user message. The agent must not call a tool in the same turn it asks a quick-reply question.
7. The full conversation (including tool messages) is persisted to `<userDir>/chat/<threadId>.json` so follow-ups retain context — the client does **not** resend history.

**Frontend**: `ChatPanel.jsx` is the reusable chat component — multi-turn transcript with Markdown (`react-markdown` + `remark-gfm`), live token streaming + tool-call chips over the shared Socket.IO connection (`presignSocket.js`), quick-reply chips, a Stop button (client-side `AbortController`), and suggested prompts. Chat links (SSO authorize links, presigned URLs) render with `target="_blank"` so they open in a new tab and never disturb the app session. It supports two modes: **uncontrolled** (owns its own thread) and **controlled** (parent owns `threadId`). Chat lives only on its dedicated page — `pages/ChatPage.jsx` (`/chat`), the ChatGPT/Cursor-style layout that runs ChatPanel controlled with a left sidebar listing prior sessions (`chatThreads`); clicking one loads its transcript (`chatThread`). Each session has a **right-click context menu** (and a `⋯` button) with **Rename / Summarize / Delete**; all three use themed Bootstrap `Modal`s — no native `window.confirm`/`prompt`. Rename and delete call `renameChatThread`/`deleteChatThread`; Summarize calls `summarizeChatThread` and renders the returned Markdown in a modal. The dashboard (`DashboardPage.jsx`) is full-width presign/invoke only — no chat panel.

### Cursor as a chat backend (`lib/chat/cursorAgent.js`)

**A Cursor key cannot answer a turn the normal way, and the way in is the other direction.** Cursor sells an agent, not model access: there is no `/chat/completions`, and its Cloud Agents API owns the tool loop with nowhere to hand tool *results* back — so no amount of adapter work makes it an OpenAI-shaped row. But SignBridge *is* an MCP server exposing every dashboard tool, and Cursor's agent consumes MCP. So rather than Cursor lending us a model, SignBridge lends Cursor the tools and lets its loop drive the real dashboard API. Structurally the module is `lib/sandbox/sandboxRunner.js`: spawn a process, stream it, cap it, time it out, allow cancel — with every decision (argv, MCP config, prompt, event mapping, line splitting) a pure function so `test/cursorAgent.test.js` needs no CLI, key or network.

The chosen surface is the **local CLI** (`agent --print`), not the cloud API, because the tools live at `https://localhost:2443` — nothing has to be reachable from Cursor's infrastructure, and a localhost-only app with no login stays localhost-only.

Six things are load-bearing:

- **`--force` is mandatory.** In headless `--print` mode the CLI asks for approval before each tool call and there is no terminal to answer: the spike hung the full 300 s emitting zero events, and `--trust` alone produced *"MCP call 'signbridge-list_profiles' was rejected by you"*. `--force` is Cursor's Run Everything switch, which also grants shell and file access in the working directory — hence the next point. Argv order is fixed and asserted: `--print --output-format stream-json --stream-partial-output …` with the prompt **last**. `--stream-partial-output` is what makes assistant text arrive as deltas instead of one block at the end.
- **The working directory is an empty scratch dir** under the user's artifacts (`<userDir>/cursorruns/<threadId>`), containing nothing but the generated `.cursor/mcp.json` and `AGENTS.md`. Never the repo, never a home directory — the blast radius of "run everything" has to be a directory whose entire contents SignBridge wrote. Path components are sanitised, so a `threadId` of `../../../etc` cannot escape.
- **Declaring an MCP server is not approving it**, and the approval is by name. `.cursor/mcp.json` only tells the CLI the server exists; a separate per-name approval in the CLI's own state decides whether it loads. Proved by bisection: identical prompt and config, unapproved → the agent found 0 profiles; after `agent mcp enable signbridge` → 25. `ensureMcpApproved()` runs that one command. It deliberately does **not** pass `--approve-mcps`, which approves *every* server in the user's config — on a developer machine that is their Slack, Jira and GitLab servers silently loaded into a SignBridge chat. `test/cursorAgent.test.js` strips comments from the source and asserts the flag never appears in code.
- **The MCP server is declared by `url`, not as a stdio child, and the certificate is trusted by *addition*.** Both halves of the original design were falsified in the container. A **stdio** entry is subject to **MCP Network Controls**, an account/team-level Cursor policy that forces the server to run inside Cursor's own sandbox; that sandbox does not exist in a container, so the CLI refuses to start the server — *"requires sandboxing because MCP Network Controls are enabled, but the sandbox is not supported on this platform"* — and the turn runs with **zero tools while looking completely healthy** (the agent politely reports it cannot see a SignBridge server). Cursor's CLI skips that requirement for entries carrying a `url`, so `buildMcpConfig` emits `{"url": "<apiBase>/mcp"}` — SignBridge's own in-process Streamable HTTP endpoint, so still nothing is spawned and nothing is exposed. The self-signed cert that made the URL form look impossible is solved by `buildEnv`: SignBridge spawns the CLI, so it sets **`NODE_EXTRA_CA_CERTS`** to `<keysDir>/<ssl.CERTNAME>` for that one child, which *adds* a trust anchor instead of disabling verification — and it **deletes** any inherited `NODE_TLS_REJECT_UNAUTHORIZED`, because a blanket opt-out would also cover the CLI's own authenticated calls to Cursor's API. Verified in the container: `agent mcp list-tools` printed the whole tool set, and a live turn called `list_profiles`. `mcp/node_modules` is still required (the endpoint is served by `mcp/mcpHttp.mjs` in this process).
- **The key is never in argv.** It is unsealed at spawn time and passed as `CURSOR_API_KEY` in the child's own environment, so it cannot show up in `ps` or in a logged command line — the same invariant as `sandboxCredentials.js`. The test scans every `args.push(...)` for a credential and every log/write line for `apiKey`.
- **The system prompt goes on the first turn only.** `buildPrompt` sends the full instructions plus the tool note when starting a conversation, and only the new message when resuming — the CLI keeps its own history, so re-sending them would present the instructions as fresh user input every turn. Continuity comes from `system/init`'s `session_id`, which is persisted as `cursorChatId` on the thread (`threadStore.setMeta`) and replayed as `--resume`.

`mapEvent` translates Cursor's event vocabulary into the same emitter events the in-process agent produces — `system/init` → the chat id, `assistant` deltas (`message.content[0].text`) → tokens, `tool_call/started|completed` → tool chips using the bare `toolName` with `result.success` deciding how the chip closes, `result/success` → the final answer, `thinking/*` recognised but not forwarded. **An unknown event returns `null` rather than throwing**, so a CLI release that adds an event type degrades to silence instead of breaking every turn.

**The CLI echoes each finished message block, so streaming needs `absorbAssistantText`.** With `--stream-partial-output` a paragraph arrives as dozens of small `assistant` deltas and is then repeated **once in full** in one more `assistant` event, just before the next tool call or the result — so plain concatenation prints the whole answer twice (a captured stream: 834 characters streamed for a 417-character reply). Nothing on the event distinguishes the echo (`timestamp_ms` was absent on only one of the two), so it is identified by *being* the block just streamed: a pure reducer over `{buffer, deltas}` drops an event whose text equals the accumulated buffer, and requires the buffer to have come from **more than one delta** so a genuinely repeated short token (`"."` then `"."`) is not swallowed. An echo carrying more text than was seen emits only the remainder. Belt and braces on top: the persisted answer prefers the `result` event's text, which is the CLI's own complete answer and structurally immune to however deltas get chunked; the streamed text is the fallback for a turn with no result (e.g. cancelled mid-answer).

`preflight()` checks the two independently breakable things — the CLI exists on this machine, and `mcp/node_modules` is installed — caches the answer for 30 s, and **never errors**: a missing CLI is a normal reported state, exactly as Sandbox reports a missing Docker socket. `testLlmConnection` calls `invalidatePreflight()` then `preflight()` and persists the result as `backendStatus`, which is what lets Settings say "key verified, but the CLI is missing" instead of one ambiguous failure. A turn attempted anyway fails with `cursorBackendNotReady`, which `chatService` turns into a 503 carrying `reason:'backend_not_ready'` + `needsLlmSetup:true` — the same contract as an unconfigured provider, so `ChatPanel` offers Settings rather than "try again".

**Caveats worth stating plainly, because they are not visible from the Settings form:** the CLI must be installed on the machine running SignBridge (the process that spawns it) — **the Docker image installs it** (see the `INSTALL_CURSOR_CLI` build arg in the `Dockerfile`, which also runs `npm ci` in `mcp/`), so the normal deployment needs nothing extra, but a build with `--build-arg INSTALL_CURSOR_CLI=0`, an offline build, or a local `npm start` on a machine without it will report the CLI missing rather than failing a turn; `--force` grants shell and file access inside that scratch workspace; and any MCP servers the user has approved globally in their own Cursor CLI state also load for these runs. Configuration is the `[cursor]` section of `config.properties` (`cliBin`, `runsDirName`, `mcpServerName`, `timeoutSeconds`, `maxOutputBytes`, `maxConcurrentRunsPerUser`), with `CURSOR_CLI_BIN` as the one env override.

### Sandbox mode (`lib/sandbox/`)

The third invocation mode, alongside `Rest_Api` and `Cli`. Instead of a form, the user gets an in-browser IDE (Monaco) and writes **Python / JavaScript / TypeScript / Java**; pressing Run executes that code in a throwaway Docker container that already has the selected profile's AWS credentials in its environment. It exists because SigV4 presigning is an advanced niche — most developers would rather write five lines of boto3 and see what happens.

Modules (all CommonJS, all callback-style like the rest of `lib/`):

| Module | Responsibility |
| --- | --- |
| `sandboxRuntimes.js` | The language registry: `RUNTIME_ORDER = ['python','javascript','typescript','java']`, per-runtime entry file, run/check commands, preinstalled library list, and the AWS + Generic-REST starter templates. **Adding a language means adding an entry here** (plus the image). |
| `sandboxCredentials.js` | Turns a profile into the *standard* AWS env vars (`AWS_ACCESS_KEY_ID`, `AWS_SECRET_ACCESS_KEY`, `AWS_SESSION_TOKEN`, `AWS_REGION`) so boto3 / SDK v3 / SDK v2 pick them up through their own default provider chains — no SDK is taught about SignBridge. SSO profiles get freshly minted short-lived role credentials via `ssoUtils.getSecurityToken`. Only `iam_user` / `sso_user` yield credentials. |
| `sandboxRunner.js` | Builds and spawns the `docker run` command; enforces the timeout, output cap, and resource caps; writes/cleans the per-run workspace; `preflight()` (Docker reachable + image present) and `cleanupStaleWorkspaces()` are called from `server.js` at startup. |
| `sandboxDiagnostics.js` | Parses real compiler/interpreter output (CPython tracebacks, Node ESM stacks, `tsc` TS-codes, `javac`) into `{ line, column, severity, message, code }` markers for Monaco. |
| `sandboxRemedies.js` | Maps a marker or a runtime error to actionable fixes — including credential-aware ones (`ExpiredToken` → run `aws sso login --profile <name>`). |
| `sandboxCompletions.js` | AWS-aware completions: reads botocore service models and exposes clients/operations/shapes. `xformName()` reproduces botocore's `xform_name` exactly (verified against all ~15k operations), so users see `describe_vpcs`, not `describe_vp_cs`. |

| `sandboxService.js` | The Express handlers for the routes below; resolves the profile, orders credential resolution before the run, and shapes responses. |

Execution & isolation (`sandbox/`): `sandbox/Dockerfile` builds `signbridge-sandbox:latest` (Python 3.11 + boto3, Node 20 + AWS SDK v3 + `tsc`, JDK + AWS SDK v2 resolved from `sandbox/pom.xml`). It is built automatically by `docker compose up` (the one-shot `sandbox-image` service) and by `launchSignBridge`; `npm run build:sandbox` is the manual path for local `npm start` runs. Each run gets a fresh workspace mounted **read-only**, a writable tmpfs at `/tmp`, `--network none` for Validate, and memory/CPU/pids caps — all from `[sandbox]` in `config.properties`.

Two invariants worth preserving:

- **Secrets never enter argv.** Credentials are passed as `docker run -e NAME` (bare name, no `=value`) and supplied through the spawned process's own `env`, so nothing lands in the process table. Anything user-visible goes through `describeCredentials()`, which masks.
- **The `-v` source must be a *host* path.** `docker run` mount sources are resolved by the daemon on the host, so when SignBridge itself runs in a container the workspace has to be named by its host path. `SANDBOX_HOST_BASE_DIR` (set by `docker-compose.yml` / `launchSignBridge`) drives `sandboxRunner.toHostPath()`; without it Docker would silently create an empty directory and every run would fail with "no such file". The workspace path stays local for writing and cleanup — only the mount argument is translated.

**Frontend**: `components/SandboxIde.jsx` (Monaco wiring in `components/monacoSetup.js`) — language + template picker, Run / Validate / Stop, an output pane, inline diagnostics with remedy chips, and the saved-scripts list. It renders in **two modes**, and the difference is only which pickers it owns:

- **Embedded** — `invocationMode === "Sandbox"` in `PresignDashboard.jsx` is a genuine third form state: selecting it swaps the request form for `<SandboxIde embedded>` **in place**, exactly the way selecting `Cli` swaps it for the command box. Nothing navigates. The dashboard's own profile + auth-mechanism selectors stay in view above the editor and are passed down as props (the parent's selection is authoritative and overrides any profile stored in a saved script), so the editor hides its own profile/auth dropdowns and shows a read-only **Credentials** badge instead — the same choice is never made twice on one screen. The Presign/Invoke button row, the "Processing…" placeholder, and the Response panel are all suppressed in this mode, because the editor owns its own Run/Validate/Stop and its own output pane.
- **Standalone** — `pages/SandboxPage.jsx` at `/sandbox` (also in the nav). No parent selection exists there, so the component shows its own profile + auth-mechanism pickers; an optional `?profile=&authnMode=` query seeds them.

### S3 World (`lib/s3/`)

A bucket browser whose point is **viewing**. The console (and every S3 explorer built on it) stops at list/upload/download: to read a parquet file, a gzipped log, a spreadsheet or a 4 GB NDJSON dump you download it and switch applications. S3 World decodes it server-side and shows it.

| Module | Responsibility |
| --- | --- |
| `s3World.js` | The Express handlers, the recursive search traversal, and the limits (`PREVIEW_HEAD_BYTES` 512 KB, `WHOLE_OBJECT_LIMIT` 32 MB, `UPLOAD_LIMIT_BYTES` 100 MB, `SEARCH_DEFAULTS` 200 k keys / 1 k matches). Also `clampExpiry()` — pure and clock-injected. |
| `s3Client.js` | The S3 REST calls (ListBuckets/ListObjectsV2/Head/Get with `Range`/Put/DeleteObjects/CopyObject/GetBucketLocation) and the bucket-region cache. **`listBuckets` always sends `max-buckets`**: S3 includes `BucketRegion` per bucket only when the request carries at least one valid parameter, so that one query param is what populates the Region column for zero extra calls (and seeds the region cache, sparing later wrong-region retries). It also opts into pagination — hence the `continuation-token` loop, without which an account over the page size would silently list short. |
| `s3Sign.js` | SigV4 for S3 specifically (`UNSIGNED-PAYLOAD`, presign with query overrides). Routes its signature through `lib/sigv4.js`. |
| `s3Endpoint.js` | Virtual-host vs path style, and the region-specific host. |
| `s3ContentTypes.js` | Type resolution — extension, then magic bytes, then the stored `Content-Type` — plus `isInlineSafe()`, the closed allowlist, and the `viewer` a type maps to. |
| `s3Preview.js` | The decoders. Returns `{ kind, … }` where kind is `table` (csv/tsv/parquet/ndjson), `json`, `xml`, `yaml`, `text`, `markdown`, `html`, `archive`, `sheets`, `document`, `notebook`, `hex` or `error`. `previewTar` is hand-written (no dependency) because `.tar` / `.tar.gz` is how model artifacts and log batches arrive in S3. |
| `s3Xml.js` | XML → an element tree, for the collapsible viewer. Hand-rolled and pure (string in, tree out) because xml2js is a *deserialiser* — it discards document order, and `previewBuffer` is synchronous while xml2js is callback-based. Custom DOCTYPE entities are deliberately **not** expanded: that is the billion-laughs DoS, and object bytes are untrusted, so safety is by construction rather than by limit-checking. |
| `s3Yaml.js` | YAML → a key tree, same contract. Also hand-rolled and pure: js-yaml would give back JS *values* (`1.0` → number, `on` → boolean, comments gone), and a viewer must show the document, not a decoded approximation — so every scalar stays source text. Block YAML only; flow collections stay one-line scalars. |
| `s3Search.js` | The search language, as pure functions over `{ key, name, size, lastModified }`. No I/O, no fixtures in its tests. |

Seven things to preserve:

- **Which route an object takes is a security decision, not a cosmetic one.** `recommendView()` returns `tab` | `preview` | `download`. `tab` means a presigned URL on the **S3 origin** — a different origin, no ambient credentials, and (being a top-level navigation) no bucket CORS needed. `preview` means the bytes were decoded here into JSON, so nothing untrusted executes. An S3 object is attacker-controlled input, and SignBridge's own origin holds AWS credentials; HTML or SVG served inline from it would run with full access to that DOM. `s3ContentTypes.isInlineSafe()` is the allowlist (`image/*`, `video/*`, `audio/*`, `application/pdf`, `text/plain` — explicitly **not** SVG, HTML, XHTML, XML). Extend it with care. SVG resolves to the image viewer but is flagged `scriptable`, so it previews as inert text.
- **Parsing happens on the server.** Reading object bytes from browser JS is a cross-origin fetch needing a CORS policy on each bucket, and S3 World targets buckets the user may not own. Doing the reads server-side means it works on any bucket the credentials can read, with zero configuration.
- **Previews are ranged, but a document is not a stream.** `planPreviewRead()` (pure, in `s3World.js`) makes the call, and it splits formats three ways. **Streams** — logs, source, CSV, NDJSON — read only the first `PREVIEW_HEAD_BYTES`, which is what makes a 40 GB log open instantly. **Documents** — JSON, XML, YAML — are read *whole* while affordable, because the closing bytes are part of the syntax: a head read leaves JSON unparseable, so a 600 KB `.json` used to open as raw text saying "the JSON is incomplete" with no Tree tab at all. Their ceiling is `DOCUMENT_BUDGETS` (the decoder's own budget, keyed by viewer) rather than `WHOLE_OBJECT_LIMIT`, because past it the preview degrades to raw text anyway and reading 30 MB to say so is waste; over the budget they fall back to the head read rather than erroring. **Containers** — zip/OOXML (trailing central directory), gzip (cannot inflate from a prefix), notebooks — need every byte and are *refused* above `WHOLE_OBJECT_LIMIT`, since there is no partial answer to give. Parquet sits outside all three: `s3AsyncBuffer()` turns hyparquet's reads into range GETs, so a multi-gigabyte parquet previews in a few KB of traffic. Relatedly, `previewBuffer` hands the JSON decoder the **full** decoded text, not the `MAX_TEXT_CHARS` slice the text viewer gets — slicing first would report a complete object as incomplete.
- **The octet-stream fix is signed.** `s3PresignView` puts `response-content-type` / `response-content-disposition` **inside** the signature, so a PNG stored as `application/octet-stream` renders in a tab, and a caller cannot append their own override to a URL we issued.
- **A PDF is framed from the S3 origin, not from the object proxy.** `GET s3Object` serves untrusted bytes from SignBridge's own credential-holding origin, so it sends `Content-Security-Policy: default-src 'none'; sandbox; frame-ancestors 'none'` — and `frame-ancestors 'none'` means *nothing here can frame it*. Images, video and audio are unaffected (`<img>`/`<video>` are not documents), but a PDF has to be framed, so pointing an `<object>` at the proxy silently produced the fallback message instead of the document. `S3ObjectViewer.jsx` therefore mints a short-lived presigned URL (`s3PresignView`, `disposition: 'inline'`) for the PDF frame — the same URL "Open in new tab" uses — with the proxy URL as a fallback when presigning fails. Don't "simplify" it back to the proxy URL: the CSP is deliberate and the regression is invisible until someone opens a PDF.
- **A structured preview degrades to raw text, never to an empty tree.** `previewXml` / `previewYaml` return `kind:'xml'` / `kind:'yaml'` on success and `kind:'text'` with `valid:false` and a note *saying why* when the parse throws or finds no structure. Both parsers are forgiving on purpose (a ranged read leaves XML elements open; YAML in the wild has unquoted values), but a tree that misrepresents the document is worse than showing the bytes — so anything genuinely ambiguous throws and falls back. Keep that contract when adding a format: the client has no way to tell a wrong tree from a right one.
- **`previewBuffer` dispatches on the resolved `contentType`, never on the extension.** The whole point of `resolveObjectType` is that the extension may be absent or misleading — a Tableau `.twbx` is a zip, and plenty of objects have no extension at all. An earlier version branched on `type.extension`, so an archive correctly identified from its magic bytes was fetched in full and then hex-dumped. Add a format by matching its `contentType` under the right `viewer`.

**Search** inverts the console's defaults (see the header comment in `s3Search.js` for AWS's own wording of its limits): a bare word matches **anywhere** in the key, **case-insensitively**, **recursively** from wherever you are. Opt-in syntax: `"exact phrase"`, `*.log` globs, `-exclude`, `ext:csv,tsv`, `size>10mb`, `modified>7d`, `/regex/`. Anything unparseable degrades to a substring term rather than erroring — a search box that rejects input is worse than one that finds too much. The walk streams `search_progress` over Socket.IO every 5 000 keys and is cancellable by `searchId`, so a million-key bucket is watchable and stoppable.

**A search has a `scope`, and folders are results too.** "Where is the invoices folder?" and "which files are called invoice?" are typed identically, and against `invoices/2026/summary.csv` the default answers both at once — so `scope` says which was meant: `'name'` (the last path segment only), `'folder'` (the directory path the object sits in, *and* that folder's own name), or `'both'` (the whole key — the default and a superset). `'key'` stays a synonym for `'both'`. Three invariants: in every scope but `'name'` a term is tested against **two subjects** (the path and the last segment), because globs and regexes are anchored and `*.log` against a full key would otherwise need a leading `*/`; whenever folders are in scope the walk **derives** the matching folders from the keys already streaming past (each ancestor path judged once and memoised in `s3World.searchObjects`, since S3 has no directory listing) and reports them with an object count and rolled-up size, capped at `SEARCH_DEFAULTS.maxFolderMatches`; and `compileFolderMatcher` deliberately **ignores object-only filters** (`size>`, `modified>`, `ext:`) because a folder has none of those properties and applying them would silently zero the folder list. A zero-byte folder marker registers its folder without counting as an object, which is what makes an *empty* folder findable — something the console cannot do at all. The frontend surfaces this as a scope select in the search box (`SEARCH_SCOPES` in `S3ObjectBrowser.jsx`, which re-runs the search when it changes so the results never contradict the selector) and renders matched folders as clickable rows above the object matches.

**Previous / Next appear above the table as well as below it**, on both the bucket list and the object browser, via the shared `components/s3/Pager.jsx` — a page of 1000 keys is several screens tall and Next should never be a scroll away. Only the bottom instance takes `pageSizes` (two selects bound to one value on a single screen reads as a bug), and both instances are suppressed while a search result is on screen, which is a single result set rather than a page.

**Every failure offers a Retry that re-runs the failed operation, not a reload.** The commonest error in S3 World is an expired SSO session, and its message is *"approve this SSO session at &lt;url&gt;, then come back and retry"* — so "come back" has to lead somewhere. `components/ApiErrorAlert.jsx` is the single error surface (message, the `aws sso login` hint, an **Authorize** button that opens `verificationUriComplete` in a new tab, and **Retry**); reloading the page instead would discard the folder drilled into, the search run and the objects selected. Retry therefore re-runs *that* operation: `S3ObjectBrowser` records one per failure path (`failWith(e, retry)` — the list page with its own continuation token, the search, or the `withBusy` copy/move/delete closure), the viewer bumps an `attempt` counter to re-read the object, and the bucket list re-lists. Adding a new failing call means giving `failWith` a retry too; the alert falls back to `refresh` only so it is never a dead end. A presign/copy/download failure inside the viewer is deliberately *not* one of those: it goes to a separate `linkError` rendered **beside** the preview (Retry re-mints the link), because losing the object you were reading over a failed link would be a poor trade.

**Authorize + Retry is the same affordance app-wide, in two implementations, and that is on purpose.** `components/ApiErrorAlert.jsx` (Bootstrap) is shared by S3 World and **Sandbox** — Sandbox keeps the whole error payload rather than just its `message`, so a credential failure gets Authorize plus a **Run again** that re-runs the code (`errorNeedsAuth` gates it, since a save or template failure has nothing to re-authorize). The **dashboard** is Cloudscape, where a Bootstrap alert reads as a defect, so it renders the same two buttons through Cloudscape's `Alert` `action` slot from its own `pendingAuth` state `{ url, retry }`. That state is set by `setFormattedResponse(result, opts, retry)` and by the `formatErrorResponse` catch paths in `handlePresign`/`handleInvoke`, and by `resolveCurlRequest` (retry = `copyRequestAsCurl`); the URL comes from `extractPendingAuthUrl()` in `utils/awsRequestUtils.js`, which is exported precisely so the detection rule cannot drift between the alert and the rendered response text.

**Uploads accept a drop, and folders keep their shape.** `components/s3/S3UploadDialog.jsx` owns the queue: drop files *or whole directories* (expanded through `webkitGetAsEntry()` / `readEntries()`, which must be drained in a loop — it returns ~100 entries at a time), or use its Choose files / Choose a folder pickers, and each file's relative path is preserved so `logs/2026/app.log` lands at `<prefix>logs/2026/app.log` rather than flattened. Three deliberate details: the drop target is the whole browser panel *and* the whole modal body (a drop that misses a small dashed box is handled by the browser, which navigates away from the app to display the file — `S3ObjectBrowser` also installs a window-level `dragover`/`drop` guard for exactly that reason); progress is per file, because a 90 MB PUT with no feedback looks like a hang; and one file failing does not discard the queue — the row is marked and retried on its own, except for a credential error, which stops the run since every remaining file would hit it too. `MAX_FILE_BYTES` mirrors `UPLOAD_LIMIT_BYTES` in `lib/s3/s3World.js`, so an oversized file is refused before its bytes go on the wire.

**Socket event**: `event_s3_world_<userName>`, carrying `search_start`, `search_progress` (`scanned`, `matchCount`, `recent[25]`), `search_complete`, `delete_progress`, `copy_progress`.

**Frontend**: `pages/S3WorldPage.jsx` at `/s3world` — profile gate (AWS profiles only; one button per AWS mechanism the profile offers) → `components/s3/S3BucketList.jsx` (client-side paging + a forgiving `matchName` filter, since ListBuckets returns the whole account in one response; regions come with that response, and the per-bucket GetBucketLocation is only a fallback for endpoints that omit them) → `components/s3/S3ObjectBrowser.jsx` (breadcrumb drill-down, continuation-token paging with a token stack for Previous, selection, drag-and-drop upload via `components/s3/S3UploadDialog.jsx`, new-folder/copy/move/delete, and the search UI with its live `s3ExplainSearch` hint; errors render through `components/ApiErrorAlert.jsx`). All state lives in the query string (`?profile=&authnMode=&bucket=&prefix=`), so a deep folder is a shareable link and Back walks back up the tree. Viewing goes through `components/s3/S3ObjectViewer.jsx` (modal) and `components/s3/objectViewers.jsx` (one renderer per `preview.kind`); `pages/S3ObjectPage.jsx` at `/s3world/object` is the same body full-page, which is what makes "open in a new tab" work for content types no browser can render natively. **Monaco is deliberately not used here** — it would add a ~4.5 MB chunk to a page that only needs a line-numbered `<pre>`.

**Anything nested is navigated, not scrolled.** JSON, XML, YAML and archive listings all render through one shared collapsible tree — `components/s3/StructureTree.jsx` (expand/collapse, a filter that force-opens the path to every match and keeps a match's own subtree openable, bounded Expand all, copy-path per node) with a per-format adapter in `components/s3/treeAdapters.js` (`jsonToTree`, `xmlToTree`, `yamlToTree`, `archiveToTree`). Notebook cells collapse individually. Three things about this are deliberate: the tree component knows nothing about any format (adapters produce a single node shape, so a new format is an adapter, not a new viewer); every one of those viewers keeps a Raw / Flat tab, because "show me the actual bytes" is still legitimate; and the **JSON tree is built in the browser from `preview.text`** rather than shipped as a second nested representation — safe because that text is the server's own re-serialisation of an already-parsed document, not the object's bytes. The copied `path` is the expression for that format's idiom (`$.a.b[0]`, `/project/dependencies/dependency[2]`, `spec.containers[0].image`), which is what turns "found it in the viewer" into "can query it in code".

## Data / storage layout

File-based, everything under one fixed home base dir (`~/.signbridge`; see `lib/paths.js`). Nothing is written inside the project directory.

```
~/.signbridge/                     # fixed base dir (not configurable)
├── artifacts/
│   └── userartifacts/{userName}/
│       ├── profiles/       # imported + user-added AWS/REST profiles (myprofile.json, *_profile_details.json)
│       ├── history/        # invocation history
│       ├── favorites/      # saved favorite requests (favorites.json)
│       ├── collections/    # imported Postman-style templates
│       ├── settings/       # settings.json
│       ├── llm/            # settings.json — LLM provider config; API keys sealed (AES-256-GCM), mode 0600
│       ├── sandbox/scripts/  # saved Sandbox scripts (<scriptId>.json)
│       ├── sandboxruns/    # per-run Sandbox workspaces (created + deleted per run)
│       ├── cursorruns/     # per-thread scratch workspaces for the Cursor chat backend
│       │                   #   (.cursor/mcp.json + AGENTS.md only — never the repo, never $HOME)
│       └── public_client_creds/
└── keys/                   # mode 0700: auto-generated self-signed TLS cert + key, and
                            #   llm-secret.key (the 32-byte wrapping key for sealed LLM keys).
                            #   Both key files are 0600 — see lib/llm/ above.
```

Always build these paths via `lib/paths.js` (`getUserDir(userName)`, `getKeysDir()`), never from `os.homedir()` directly. Directory/file *names* come from the `[server]` section of `config.properties` (e.g. `historyDirName`, `settingsFileName`, `profilesDirName`). In Docker the base dir is a host mount (`~/.signbridge`), so artifacts + certs persist across rebuilds.

## Configuration (`config.properties`)

INI-style, section-prefixed keys accessed as `props.get('section.key')`:
- `[server]` — `PORT` (2443 HTTPS), the network posture (`bindHost`, default `127.0.0.1`, env override `BIND_HOST`; `allowedHosts`, comma-separated extra `Host` values) and the artifact sub-directory/file *names* (`artifactsDirName`, `userArtifactsSubDir`, `keysDirName`, `historyDirName`, `favoritesDirName`, `collectionsDirName`, `chatDirName`, `settingsDirName`, `scriptsDirName`, `profilesDirName`, `settingsFileName`). The base dir itself is fixed (`~/.signbridge`) and has no config key.
- `[logging]` — `level` (`error|warn|info|debug`, env override `LOG_LEVEL`). `debug` prints the whole signing trace, which is the only practical way to debug a signature mismatch; every level is redacted first (see `lib/logger.js` below).
- `[ssl]` — `KEYNAME`, `CERTNAME` (file names under `<baseDir>/keys`)
- `[auth]` — `defaultUserName`/`defaultDisplayName`/`defaultEmail` (the single local user; no login toggle)
- `[app]` — `routePrefix`, `projectName`, `displayName`, `tagline`, `engineName`, and `authLabel.*` display labels
- **There is no `[llm]` section.** Every part of the AI configuration — `enabled`, provider, credential, model, `reasoningEffort`, `temperature`, `maxToolIterations` — is set at runtime in Settings → AI features and stored per user (see `lib/llm/`). Don't add the section back, and don't add a single key from it: whatever is read here is a value the Settings page cannot change without a restart, and the last time `enabled` lived here the toggle in the UI was decorative. `test/secretHygiene.test.js` fails if the section reappears in `config.properties.example`.
- `[cursor]` — only used when the active AI provider is Cursor (see **Cursor as a chat backend** above): `cliBin` (env override `CURSOR_CLI_BIN`), `runsDirName`, `mcpServerName`, `timeoutSeconds`, `maxOutputBytes`, `maxConcurrentRunsPerUser`. An agent turn runs a whole tool loop, which is why its timeout (300 s) is generous next to a single completion.
- `[sandbox]` — Sandbox execution: `image` (`signbridge-sandbox:latest`), `dockerBin`, `runsDirName`, `timeoutSeconds` / `checkTimeoutSeconds`, `memoryLimit` / `cpuLimit` / `pidsLimit`, `tmpfsSize`, `maxOutputBytes`. Saved-script *directory names* (`sandboxDirName`, `sandboxScriptsDirName`) live in `[server]` with the other artifact names.
- `[awscatalog]` — botocore service-model source shared by the Templates page and Sandbox completions (`lib/awsCatalog.js`): `modelBaseUrl`, `modelCacheDirName`, `defaultRegion`

`config.properties` itself is **gitignored**; only `config.properties.example` is tracked. Copy the template on setup. The Dockerfile seeds a default from the example, and compose bind-mounts the host's real file at runtime.

**There is no `.env` file, and no `dotenv` dependency.** `config.properties` is the configuration surface; the environment is for the handful of values a deployment has to set from outside it (compose's `environment:` block, a systemd unit, a Kubernetes env). `.env.example` was removed deliberately — a tracked template for a file that holds an API key is how the key ends up in a commit, and the LLM key now lives encrypted under `~/.signbridge` (see `lib/llm/`). Don't reintroduce either the file or the dependency: `server.js` reading `.env` would silently make an untracked file authoritative over the tracked one.

The environment variables the app actually reads: `BIND_HOST`, `LOG_LEVEL`, `USER_NAME`, `CURSOR_CLI_BIN`, `TIMEOUT` (the HTTP timeout the signers and REST callers use), the credential-refresh buffers (`SSO_CREDENTIAL_REFRESH_BUFFER_MS`, `EC2_CREDENTIAL_REFRESH_BUFFER_MS`, `IRSA_CREDENTIAL_REFRESH_BUFFER_MS`), and Sandbox's `SANDBOX_IMAGE`, `SANDBOX_DOCKER_BIN`, `SANDBOX_HOST_BASE_DIR` (the host path that `~/.signbridge` is mounted from — required only when SignBridge itself runs in a container; see Sandbox mode above). `mcp/server.js` additionally reads `SIGNBRIDGE_API_BASE` and `SIGNBRIDGE_USER`, but it is a separate process in the *client's* environment, not the server's.

There is **no** env var for the base dir — it is always `~/.signbridge`. Two variables look like app config and are not: `HTTPS_PORT` and `BIND_ADDRESS` are read by **compose and `launchSignBridge`**, where they set the *host* side of the `${BIND_ADDRESS:-127.0.0.1}:${HTTPS_PORT:-2443}:2443` publish. The server's own listen port comes from `server.PORT` and is always 2443 inside the container — don't make `server.js` read `HTTPS_PORT`, or a remapped host port would stop matching the container port. `config.properties` is gitignored; only `config.properties.example` is tracked.

**No environment variable configures AI features — not a key, and not an on/off switch.** The only way is Settings → AI features, which verifies the credential and stores the whole configuration per user (see `lib/llm/`); `LLM_API_KEY`/`LLM_MODEL`/`LLM_BASE_URL` and `LLM_ENABLED` are all deleted, not merely undocumented. Chat is enabled by default, so with no provider configured the chat endpoint returns 503 with `needsLlmSetup:true` and a message pointing at Settings, and the Chat page shows that banner before a turn is even sent. An unattended deploy that cannot reach the Settings page therefore gets a SignBridge with AI features effectively off — which is the correct outcome, since AI features need a credential nobody has chosen. An operator who wants them off for real turns the switch off in Settings, and it applies to the next message rather than the next restart.

## Running the app

**Docker (primary path):**
```bash
docker compose up --build -d
# open https://localhost:2443/signbridge/dashboard  (accept self-signed cert)
```
Or use the helper: `./launchSignBridge start|stop|delete` (builds the image and wires `~/.aws` mounts).

**Local backend:** `npm start` (`node server.js`) — requires `frontend/dist` to exist.

**Frontend dev:** `cd frontend && npm install && npm run dev` (Vite dev server proxies `/signbridge` to `https://localhost:2443`).

**Frontend build:** `npm run build:web` (root) or `cd frontend && npm run build`.

**AWS credentials:** mount `~/.aws` (`config`, `credentials`, `sso/`). For SSO, run `aws sso login --profile <name>` on the host first. Profiles auto-import into user artifacts on startup.

**AI features (Chat):** no file to edit and no key to put anywhere on disk. Open **Settings → AI features**, turn on Enable AI features, pick a provider, then paste an API key (or, for Bedrock, sign with an AWS profile you already have); SignBridge verifies the credential and lists the models it can actually reach. The key is stored encrypted under `~/.signbridge` and the chosen model is shared by every AI surface. There is no environment variable and no config key that can supply a provider key instead — until one is added in Settings, the Chat page says so and links there. The same page holds the agent's behavioural knobs (reasoning effort, temperature, max tool iterations) and the switch that turns everything off; all of it applies to the next message, with nothing to restart.

**AWS Bedrock (Claude) needs no key at all if you already have an AWS profile here.** Pick Bedrock, leave the credential source on **Sign with an AWS profile**, choose one of your existing profiles (IAM user, SSO role, EC2 instance role, or EKS IRSA service account), set the region Claude is enabled in, and press Save & test. The role needs `bedrock:InvokeModel` and `bedrock:InvokeModelWithResponseStream` on the models you use; `bedrock:ListFoundationModels` is optional — without it the picker offers a short list of current Claude models instead of your account's, and you can type any other model id you have access to (an inference profile, a foundation model, or a provisioned-throughput ARN) into **Or use a specific model id**; it is remembered and joins the list. Chat works either way. A Bedrock API key is the alternative for anyone who has one.

**The Cursor provider needs two things besides a key**, because it is the one provider answered by a local process rather than an endpoint (see **Cursor as a chat backend** above): the Cursor CLI on the machine running SignBridge, and SignBridge's MCP dependencies. **The Docker image ships both** — the `Dockerfile` installs the CLI (`INSTALL_CURSOR_CLI=1`, and a failed install is a warning, not a failed build) and runs `npm ci` in `mcp/` — so `docker compose up --build` is all that is needed. For a local `npm start`, install them once: `curl https://cursor.com/install -fsS | bash` and `cd mcp && npm install`. **Test connection** reports both separately from the key, so a missing piece is named rather than guessed at. Two consequences to be aware of before choosing it: the headless CLI runs with tool approval forced (`--force`), which also grants it shell and file access **inside its scratch workspace** — hence that workspace being an empty per-thread directory holding only the generated `.cursor/mcp.json` and `AGENTS.md` — and any MCP servers already approved in your own Cursor CLI state will also load for these runs.

**Sandbox mode:** no separate setup step. `docker compose up` builds the execution image via the one-shot `sandbox-image` service, which the app service waits on with `depends_on: { condition: service_completed_successfully }`; the image's default `CMD` prints its toolchain versions and exits 0, so it doubles as a build check. It is tagged `${SANDBOX_IMAGE:-signbridge-sandbox:latest}` and `pull_policy: build` keeps compose from trying to pull that local-only name. `launchSignBridge` builds it too, but only when missing, and a failed build there is a warning rather than a hard stop. `npm run build:sandbox` (`./sandbox/build-sandbox-image.sh`) remains the manual path for a local `npm start` run. Either way Docker must be reachable from the server process. When SignBridge runs in a container that means bind-mounting the daemon socket (`-v /var/run/docker.sock:/var/run/docker.sock`) and setting `SANDBOX_HOST_BASE_DIR`; both `docker-compose.yml` and `launchSignBridge` do this, and `docker-entrypoint.sh` adds `www-data` to the socket's group (by gid, not `chmod 666`). Mounting the socket is a privileged grant — opt out with `SIGNBRIDGE_SANDBOX=0` (helper script) or by removing the volume. `server.js` runs `sandboxRunner.preflight()` at startup and logs whether Sandbox is ready; the Sandbox page reports the same, so a missing image or socket never fails silently.

**MCP:** two transports over the same tool set (`mcp/tools.mjs`), both thin clients of the HTTPS API (so the main server must be running):
- **HTTP (single service):** already served by `node server.js` at `https://localhost:2443/signbridge/mcp` — nothing else to run. Point an HTTP-capable MCP client there.
- **stdio (Claude Desktop / Cursor / Codex):** `mcp/` is published as the **`signbridge-mcp`** npm package, so the client config is `"command": "npx", "args": ["-y", "signbridge-mcp"]` with optional `SIGNBRIDGE_API_BASE` / `SIGNBRIDGE_USER` env (both default to the local install). From a clone: `node /abs/path/mcp/server.js`. From the repo without cloning: `github:rajesh-bijja/signbridge#main::path:mcp` — **`::path:` is the subdirectory separator**; `#main:mcp` parses as a git spec with no committish and no subdir, so npm installs the repository root, which has no `signbridge-mcp` bin, and the client reports only that it could not determine an executable. `mcp/README.md` is the npm package page (shipped in `files`, so it must exist); the root README's "MCP Server" section carries the full client snippets.

Four invariants of that package, all pinned by `test/mcpPackaging.test.js` because each one works in this checkout and breaks only once installed:
- **`stdout` is the JSON-RPC channel.** A single `console.log` corrupts the stream and the client reports the server as broken with nothing pointing at the print statement. Diagnostics go to `process.stderr`, which clients surface in their logs. The only stdout writes are `--help` and `--version`, both before `server.connect(`.
- **Every import must be a declared dependency of `mcp/package.json`, and nothing may reach outside `mcp/`.** The published package is that directory alone. `zod-to-json-schema` was imported by `tools.mjs` while only the MCP SDK depended on it — it resolved here through hoisting and would have died at module load the day the SDK dropped it. Both manifests now declare it, because `mcp/tools.mjs` is loaded by the backend too.
- **`NODE_TLS_REJECT_UNAUTHORIZED` is not part of the setup.** `mcp/server.js` builds its own `https.Agent` for SignBridge's self-signed cert; the env var is a *process-wide* opt-out that would also cover whatever else the client's Node process talks to. No doc may recommend it (asserted).
- **An unreachable SignBridge is a named condition, not a crash.** Clients routinely spawn their MCP servers before the app is up, so the startup `/session` probe reports the cause on stderr and never exits, and `describeTransportError` turns `ECONNREFUSED` into an instruction rather than letting a model relay "connect ECONNREFUSED 127.0.0.1:2443" as though the tool itself were broken.

Tools (58, full dashboard parity): invoke — `invoke_api`, `presign_url`, `invoke_aws_cli`, `test_bearer_token`; sandbox — `list_sandbox_runtimes`, `get_sandbox_template`, `run_sandbox`, `check_sandbox`, `list_sandbox_scripts`, `get_sandbox_script`, `save_sandbox_script`, `delete_sandbox_script`; s3 world — `list_s3_buckets`, `list_s3_objects`, `search_s3_objects`, `explain_s3_search`, `head_s3_object`, `preview_s3_object`, `presign_s3_object`, `create_s3_folder`, `upload_s3_object`, `delete_s3_objects`, `copy_s3_objects`; profiles — `list_profiles`, `check_profile_exists`, `create_profile`, `update_profile`, `delete_profile`; ec2/irsa discovery — `test_ec2_connection`, `list_irsa_clusters`, `list_irsa_service_accounts`, `describe_irsa_role`, `test_irsa_connection`; history — `list_history`, `get_history_details`, `delete_history`, `label_history`, `add_history_to_favorites`; favorites — `list_favorites`, `get_favorite_details`, `delete_favorite`, `label_favorite`; templates — `list_collections`, `import_collection`, `delete_collection`, `delete_collection_request`, `list_aws_catalog_services`, `import_aws_catalog_service`; settings — `get_settings`, `update_settings`; llm config — `list_llm_providers`, `list_llm_models`, `set_llm_model`; chat sessions — `list_chat_sessions`, `get_chat_session`, `rename_chat_session`, `summarize_chat_session`, `delete_chat_session`. Note: `list_history`/`list_favorites` return summary metadata only (no endpoint/headers/body) — use `get_history_details`/`get_favorite_details` by id to get the full request before re-invoking. Add or change tools in `mcp/tools.mjs` (both transports pick them up). `run_sandbox` takes `runtimeId` + `code` and never accepts credentials — the profile is named and the server resolves them; its `runtimeId` enum is a literal copy of `sandboxRuntimes.RUNTIME_ORDER` (this module is ESM and cannot `require()` the CommonJS registry), kept honest by `test/mcpSandboxTools.test.js`. The S3 tools are the reason an IDE client can read an object's *contents*: `preview_s3_object` returns decoded rows/text/entries as JSON, and `search_s3_objects` matches a fragment anywhere in a key across a whole subtree — neither is expressible as `aws s3 ls`. `test/mcpS3Tools.test.js` asserts every path they post to is actually mounted in `server.js`, that they all stamp the resolved user, that none accepts a credential field, and that `delete_s3_objects` keeps its "cannot be undone"/recursive warning (an LLM calling it has no undo). The EC2/IRSA discovery tools are how an IDE client fills in a profile it cannot see a form for; they post **top-level** bodies (those handlers read `req.body`, not `req.body.options`) and accept no credential field. `test/mcpProfileTypeTools.test.js` pins that, plus the two things that rot silently: that `AWS_AUTHN_MODES` still matches `lib/authnModes.js`, and that `create_profile` and `update_profile` accept exactly the same field set (they were two copies of one literal). The three LLM-config tools are read-mostly on purpose — `set_llm_model` is the only write, and there is deliberately no tool for testing a key or deleting one, because an MCP client *is* an LLM and should not be able to write a credential or spend the user's provider quota creating another. `test/mcpLlmTools.test.js` asserts that omission holds (the routes stay mounted in `server.js`; `mcp/tools.mjs` never references them).

**Parity is enforced, not aspired to (`test/mcpToolParity.test.js`).** "The MCP tools should cover the dashboard" is the kind of claim that is true on the day it is written and quietly false a month later, because the failure is an *absence* — nobody notices the tool that was never added. So the test enumerates every route mounted in `server.js` and requires each one to be either reachable from a tool or listed in an `EXCLUDED` map **with a reason**, in one of four documented kinds. A new route therefore fails the suite until someone decides which it is. It also fails on a *stale* exclusion (a route that no longer exists), so the map cannot rot into a list of ghosts.

**Three routes are excluded permanently, and the reason is the transport rather than the risk.** A tool result becomes part of the model's conversation history, so with a hosted client it leaves the machine and lands in a third party's logs. `copyBearerToken`, `getRoleCredentialsForUser` and the curl-command builder each return a **live credential as their entire payload** (the last one a signed `Authorization` header), which makes them exactly the wrong shape for a tool no matter how careful the caller is. `scrubForModel` in `mcp/tools.mjs` is the second line of defence for everything else — it runs over every tool result, so a response that merely *contains* a credential field is redacted before the model sees it (verified on the wire: `awsSecretAccessKey` redacted, `awsAccessKeyId` masked to `AKIA****NKPR`). `test/mcpRedaction.test.js` pins that, and the ownership boundary it implies: redaction belongs to the tool layer, because both transports share it and the dashboard's own responses are a different audience.

**All three `callApi` implementations share one contract** — the stdio server, `mcpHttp.mjs`, and the chat agent's loopback client each implement `callApi(pathName, payload, options)` with `options = { method, query, contentType }`. They are separate functions by necessity (different processes, different HTTP agents), so `test/mcpToolParity.test.js` asserts the signature and the three behaviours a tool depends on: a `get` uses `axios.get`, a non-post method dispatches through `axios[method]`, and `options.query` becomes `config.params`. Without that, a tool added against one transport works in Chat and 404s over stdio.

## Conventions & guidance for changes

- **Backend `lib/` is CommonJS** (`require`/`module.exports`, `"use strict"`); **frontend and `mcp/` are ESM** (`import`). Match the file you're editing.
- New backend endpoints: add the route in `server.js` under `router`, implement the handler in the appropriate `lib/` module, and expose a client function in `frontend/src/components/presignApi.js`.
- New SPA pages: add the path to the `spaRoutes` array in `server.js` **and** the React route, or Express won't serve deep links on refresh.
- Read directory/file names and branding from `config.properties` (via `appConfig`) instead of hardcoding; the app is intentionally rebrandable.
- Preserve HTTPS + self-signed cert assumptions; internal/loopback calls trust the local cert through a **scoped** `https.Agent` (`rejectUnauthorized:false` on that agent). **Never set `NODE_TLS_REJECT_UNAUTHORIZED`** — anywhere, including docs and shell snippets. It is process-wide, so it also disables verification for the provider APIs, AWS endpoints and package registries the same process talks to; the scoped agent gets the one exception the self-signed cert needs and nothing else. `lib/chat/cursorAgent.js` goes one better for its child process and *adds* a trust anchor with `NODE_EXTRA_CA_CERTS` while deleting any inherited opt-out.
- **Network posture (`lib/netGuard.js`): loopback by default, and the `Host` header is checked.** SignBridge has no login and can sign with every AWS profile on the machine, so the address it binds *is* its access control — `server.listen(port)` with no host would publish an unauthenticated credential-holding API to the local network, and nothing visible would change. Three rules live in that one module, all pure and tested: `resolveBindHost` defaults to `127.0.0.1` (`BIND_HOST` / `[server] bindHost` override it; Docker sets `0.0.0.0` because a container process must bind all of *its own* interfaces, and compose publishes to `127.0.0.1` on the host instead); `isHostAllowed` refuses a `Host` this instance does not answer for with **421**, which is the DNS-rebinding defence — binding loopback is not sufficient on its own, because any page can resolve a name it controls to 127.0.0.1 and then talk to this origin as same-origin, and its own name is the one thing it cannot hide from that header; and `securityHeaders` keeps the credential-holding DOM from being framed, keeps URLs (a presigned one *is* a credential) out of `Referer`, and stops content-type sniffing.

  **The startup line about the bind is `describeBindExposure`, it is one sentence or two, and it is a `WARN` only outside a container.** 0.0.0.0 means opposite things either side of that boundary — mandatory in a container, published to the network on a laptop — so `isContainer()` (`/.dockerenv`, then `/proc/1/cgroup`; injected `fs`, never throws, since macOS has no `/proc`) picks between an **INFO** naming the host port mapping that actually limits access there and the **WARN** that names who can reach it. Both earlier versions were wrong in the same direction. The first was a single WARN advising `set [server] bindHost=127.0.0.1`: it fired on **every** normal compose startup and its fix would have made the container unreachable through its own published port — a warning that fires on the supported configuration and whose advice breaks it just teaches the reader to skip warnings. The second got the levels right and then explained container networking at paragraph length, which is not what a log line is for; a paragraph in a log is skipped, and `test/netGuard.test.js` now caps both messages at two sentences. Two phrasings are also settled by user feedback rather than taste: "every host that can reach port 2443" was read as *every process on my own laptop* (not a risk at all), so it says **other machines on your network**; and the INFO names the mapping without claiming its current value, because this process cannot see it.
- **A value from a request may become one path segment and nothing more (`lib/pathSafety.js`).** Every store here is files named by a caller-supplied id — profile name, history id, favorite id, thread id, script id — so every one of them is a traversal unless something stops it (`{ historyId: '../../llm/settings' }` reads or deletes any JSON on disk). Three stores had grown three different private guards, which is exactly how the fourth ships without one; the rule is now `assertSafeSegment` / `resolveWithin` in one module and the stores call it. `test/pathSafety.test.js` covers the classic and encoded forms and asserts the stores route through it.
- **`lib/logger.js` is the only thing that writes log output, and `lib/` contains no `console.*` at all.** Not a style preference: a `console.log` cannot be turned down by a level, does not go through the redactor, and goes to **stdout** — which is the JSON-RPC channel for anything that ever runs as an MCP stdio server. So each module takes a named logger (`const log = require('./logger').create('ssoUtils')`), calls `log.debug/info/warn/error`, and the logger decides the level (from `[logging] level` or `LOG_LEVEL`), the prefix, the stream (`warn`/`error` → stderr) and — the load-bearing part — passes **every** argument through `lib/redact.js` on the way out. That is what makes `LOG_LEVEL=debug` safe to paste into an issue: the full signing trace is there and the session token in it is not. Three exemptions, each asserted rather than trusted: the two `console.error` calls in `server.js`'s bottom-of-file `catch`, which handles "requiring `lib/` threw" — i.e. the case where the logger is the thing that is unavailable; the `console.log`s inside `sandboxRuntimes.js`, which are **not our code** but the text of the JS/TS starter templates the user runs (a well-meaning cleanup there corrupts every template, so the test asserts both that they exist and that none is real code); and `mcp/server.js`, a separate process that must not load the backend and so writes to `process.stderr` itself. `test/logger.test.js` covers the levels, the streams, the redaction of every argument shape, and those three exemptions.
- Never log or persist AWS secret keys or bearer tokens. LLM provider API keys *are* persisted, but only sealed (`lib/llm/secretStore.js`) — they must never reach a client (`llmSettings.toPublic` is the only client-facing shape), never enter a log line, and never appear in an MCP tool schema. Anything user-visible goes through `secretStore.maskKey`.
- **`lib/redact.js` is what makes that rule enforceable, and the leak it fixed was in the log, not in a response.** The SSO flow's four *success* bodies are each a credential (a client secret, a device code, an OIDC access **and refresh** token, an STS triple) and were printed in full; worse, SigV4 *signs* `x-amz-security-token`, so every signer's `canonicalHeaders` / `canonicalRequest` / assembled-headers log carried the live session token for SSO, EC2-instance-role and IRSA profiles alike. `docker logs signbridge` is the artifact people paste into a ticket, so this was the highest-yield secret in the app and nothing anywhere failed while it was wrong. Three things to preserve: **wrap the payload, don't trim the log** (`redact.forLog(value)` for objects, `redact.redactText` for a raw body or URL, `redact.redactCanonicalRequest` for canonical headers — that last one keeps the block's structure and replaces only offending header *values*, because the canonical request is the only way to debug a signature mismatch); **the rule is a substring match over key names with no allowlist**, so `tokenType` is redacted too — an allowlist is where the next leak would hide, and `test/redact.test.js` asserts that over-redaction rather than "fixing" it; and `accessKeyId` is **masked** (`ASIA****1234`), not hidden, because it answers "which credentials was that?" and is not a secret. A key naming a credentials *container* (`roleCredentials`) is walked rather than replaced, so the masked id and expiration survive. `profileUtils.redactProfileForLog` layers on top: its named-field list is the documented intent, `redact.forLog` is the backstop for a field nobody added to it. `test/redact.test.js` also source-inspects `ssoUtils.js`, so a new log line there cannot print one of these payloads raw.
- There is no login — always resolve the user via `authConfig.resolveUserName()` / `applyDefaultUserToRequest`; don't reintroduce sign-in flows.
- MCP tools must stay in sync with the dashboard: a new backend endpoint that the UI uses should usually get a matching tool in `mcp/tools.mjs`.
- **Monaco must stay out of the initial load, and that is easy to break silently.** It is ~4.5 MB — bigger than the rest of the app combined — so `vite.config.js` gives it its own chunk and only `SandboxIde` / `SandboxPage` may depend on it statically. Two failure modes have already happened: (1) importing `SandboxIde` eagerly (rather than via `lazy()`) makes the importing route pay for the editor — this is why `PresignDashboard.jsx` lazy-loads it for the embedded Sandbox mode; (2) Rollup parked Vite's tiny `preload-helper` module *inside* the monaco chunk, which made the editor a static dependency of the entry, so `index.html` grew a `modulepreload` for it plus a blocking monaco stylesheet and **every** route downloaded it. Hence the explicit `vite-preload` manual chunk. After changing chunking or adding an import to a shared component, verify with `cd frontend && npm run build` and then two checks: `grep -c monaco dist/index.html` must be **0** (that is the invariant — nothing on the critical path references the editor), and `grep -l 'from"\./monaco-editor-' dist/assets/*.js` must list only `SandboxIde-*.js`. Do **not** use `grep -l 'monaco-editor-*.js'`: the entry and `DashboardPage` chunks legitimately contain the monaco filename as a `__vitePreload` dependency *string* for the lazy Sandbox route, so that pattern reports four files and looks like a violation when nothing is wrong. A real static dependency is an `import ... from "./monaco-editor-*.js"`.
- **The brand mark is a photograph, not vector geometry, and the whole family is generated by one script.** It is a crop of `assets/signbridge-hero-source.png` — the glowing amber key standing in the tower of the Golden Gate Bridge, with the cyan request stream crossing the span behind it — so there is nothing to hand-edit and no geometry to keep in agreement across files. Every SVG is a rounded-rect clip (`rx=116` on a 512 box) around one embedded JPEG data URI; every PNG and the ICO are rasterised from the same crops. **`scripts/generate-brand-assets.sh` writes all twelve files** (`frontend/public/{favicon.svg,favicon-16.png,favicon-32.png,apple-touch-icon.png,favicon.ico,signbridge-hero.jpg}`, `assets/signbridge-logo.svg`, `assets/signbridge-wordmark{,-dark}.svg`, `assets/signbridge-wordmark{,-dark}.png` and `assets/signbridge-hero.jpg`); it needs `magick`, `rsvg-convert` and `python3`. Every file it *used* to write and no longer does was an asset nothing referenced — if you add one, give it a reference in the same change, or the next cleanup deletes it. Change the mark by editing that script and re-running it — never by editing an SVG or a PNG. The image is embedded as a data URI rather than referenced because the wordmark SVGs are rendered by rsvg-convert and (historically) by GitHub, neither of which resolves a relative `<image>` path from inside an SVG.
- **There are two crops of that photograph, and which one a file gets is decided by the size it renders at.** The **wide** crop (`360x360+600+280` of the hero) keeps the span, the cables and the cyan stream around the key; it is right from ~128px up, where those elements are visible, and it is what `assets/signbridge-logo.svg`, the wordmark tiles and `apple-touch-icon.png` (180) use. The **tight** crop (`430x430+38+45` of the wide master) is the same key filling the tile, and it is what `frontend/public/favicon.svg`, `favicon-16.png`, `favicon-32.png` and all three `favicon.ico` layers use — because `favicon.svg` is *also* the 28px navbar brand (`App.jsx`) and the tab icon, and in the wide framing at those sizes most of the pixels go to sky while the key collapses into an orange bar. Small sizes additionally get contrast and saturation pushed harder (`-sigmoidal-contrast 6x42% -modulate 108,130`), because the amber key and the red tower are close in luminance and merge once the bow is only a few pixels across; that one change is what recovered the bow's hole at 32px. **The 16px raster cannot hold that hole whatever the crop** — the key is ~4.6:1, so it is 3–4px wide in a 16px tile — and that is a measured limit, not a defect to fix: what survives there is a warm key shape against the blue tower. Every one of these numbers was chosen by rendering the result at 16/28/32/48/128px and **reading the image back**, magnified nearest-neighbour, never by inspecting markup — which is also how the wide crop's failure at 16px was found after it had already shipped. Do the same after any change, and look at all of those sizes rather than only 512.
- **The product hero is `assets/signbridge-hero-source.png` (2 MB, the source) shipped as a ~190 KB JPEG.** `assets/signbridge-hero.jpg` is embedded in the README below the wordmark — and note the README's `<picture>` points at the wordmark **PNGs**, not the SVGs: the mark is now an embedded `data:` URI and GitHub sanitises the SVGs it serves, while the PNGs are rasterised from those same SVGs and so cannot drift; `frontend/public/signbridge-hero.jpg` is the same file served through Vite's `/signbridge/` base and rendered at the top of the About page (`PresignAbout.jsx`, via `${import.meta.env.BASE_URL}`). Keep the two copies in step, and keep them JPEG — the About page is in the app bundle's path for anyone who opens it, and the source PNG is ten times the size for no visible gain at 820px wide.
- **Comparison content is single-sourced.** The "How SignBridge compares" material (matrix, differentiators, caveats) lives only in `frontend/src/data/comparison.mjs`. The About page (`PresignAbout.jsx`) imports it directly; the README block between the `<!-- BEGIN:COMPARISON ... -->` / `<!-- END:COMPARISON -->` markers is generated. Edit the data module, then run `npm run docs:comparison` to refresh the README — never hand-edit that README block.
- **Tests use `node:test`, no extra deps** (`npm test` → `node --test "test/**/*.test.js"`). The suite targets the sharp edges, not coverage: SigV4 primitives (`lib/sigv4.js`) against AWS's published vector, presigned-URL lifetime logic (`lib/expiryUtils.js`), the no-login/default-user invariant, config/branding, and secret hygiene — including the two things about the LLM subsystem that cannot fail loudly: that no recursive `chmod` reappears under the base dir (`test/llmSecretPermissions.test.js`) and that no MCP tool gains the ability to write a provider credential (`test/mcpLlmTools.test.js`). A permissions or omission regression keeps working perfectly while it is wrong, so source inspection is the only place to catch it — which is why a good half of the suite reads source rather than calling it: `test/netGuard.test.js` (that `server.js` binds the *resolved* host and checks `Host` before any handler runs, and that the shipped compose file publishes to loopback), `test/pathSafety.test.js` (that every store routes its id through the guard), `test/logger.test.js` (no `console.*` in `lib/`), `test/mcpToolParity.test.js` (every route is covered or excluded-with-a-reason), `test/mcpPackaging.test.js` (the npm package resolves, and stdout stays clean), `test/mcpRedaction.test.js`, `test/dependencies.test.js` and `test/secretHygiene.test.js`. **When adding one of these, strip comments from the source first** — these modules document their own rules in prose, so a naive regex matches the sentence describing the rule and the test passes on its own explanation. `test/redact.test.js` is the archetype: it runs the redactor over the *real* SSO/STS/OIDC payload shapes and then reads `ssoUtils.js` to assert no log line prints one of them raw. `test/cursorAgent.test.js` is the same idea applied to a subprocess: argv order, the MCP config's transport, the first-turn-only system prompt, event mapping, path sanitisation and "no credential in argv or a log line" are all asserted against pure functions and the module source, so the Cursor backend is tested with no CLI, no key and no network. Keep the signing math and the lifetime helpers **pure and clock-injected** so they stay testable — when adding logic to a request handler, extract the decision into `lib/expiryUtils.js` / `lib/sigv4.js` and test it there rather than reaching for a network mock. All four presigners route their signature through `lib/sigv4.js`; don't reintroduce inline `crypto.createHmac('sha256','AWS4'+secret)` chains.
- **Dependencies are a security surface, so the manifest is deliberately short and `test/dependencies.test.js` guards the two failures `npm audit` cannot see.** The backend runs on 19 runtime packages (Express 5, `socket.io`, `axios`, `openai`, `@modelcontextprotocol/sdk`, `zod` + `zod-to-json-schema`, `node-forge`, `ssh2`, `properties-reader`, `jsonfile`, `recursive-readdir`, `compression`, `follow-redirects`, `jwt-decode`, `xml2js`, `fflate`, `hyparquet`, `hyparquet-compressors`) — the AWS SDK is deliberately absent, since signing is what this app *is*, and `uuid` was dropped for `crypto.randomUUID()`. Prefer a Node built-in, then a small pure dependency, then nothing; adding a package means adding it to whichever manifests load it. Two traps this suite pins: (1) **an ESM-only dependency cannot be `require()`d from `lib/`**, and the failure appears *only* in the image — `require(esm)` landed in Node 20.19/22.12, so a current local Node starts fine while the container throws `ERR_REQUIRE_ESM` on the first require and never listens (exactly what a `uuid` v13 bump did); (2) **a lockfile out of step with its manifest makes `npm ci` refuse to run at all** (`EUSAGE`), which nothing local notices because `npm install`/`npm test`/`npm audit` all work off an already-correct `node_modules` — it breaks only the first clean `docker compose up --build`, i.e. only for the first person to clone the repo. Run `npm install --package-lock-only` in *both* `.` and `mcp/` and commit the locks. The `Dockerfile` tracks the `node:20-bookworm` LTS line rather than a patch pin, because a pinned patch means every rebuild carries the Node CVEs fixed since, which no `npm audit` would ever mention. The frontend carries one `overrides` entry (`dompurify: ^3.4.15`) — Cloudscape pins a transitive version with a known advisory and no release of its own to fix it, so the override is the only way to reach a clean audit; drop it when the upstream range moves, and don't add others without the same justification.
- **Sandbox logic stays pure and out of the container.** Everything worth testing in `lib/sandbox/` — diagnostics parsing, remedy selection, `xformName`, Docker argument construction, host-path translation — is a pure function, so the tests touch no fs, no network, and no Docker. Diagnostics fixtures are *real captured output* from `signbridge-sandbox:latest`; if you change a parser, capture new output rather than inventing it. Adding a language means an entry in `sandboxRuntimes.js`, tooling in `sandbox/Dockerfile`, and (because it's a duplicated literal) the `SANDBOX_RUNTIMES` list in `mcp/tools.mjs`.
